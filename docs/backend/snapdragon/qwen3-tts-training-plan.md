# Qwen3-TTS-0.6B 重训计划（v73 优化方案的第二阶段）

> 配套：[qwen3-tts-v73-plan.md](qwen3-tts-v73-plan.md)（做什么）、[qwen3-tts-predictor-redesign.md](qwen3-tts-predictor-redesign.md)（P2a 规格）、
> [qwen3-tts-opt-log.md](qwen3-tts-opt-log.md)（28 个实测实验的原始数据）。
>
> **本文的算力/数据数字是首性原理估算，不是实测**（本机没有 GPU 训练环境）。
> 估算方法写在 §3，每个数字都能按你的实际硬件重算。

---

## 0. 一页答案

| 问题 | 答案 |
|---|---|
| 卡 | **8 × A100/H100 一级（也可 1 张卡慢慢跑）**。峰值显存需求 < 40 GB/卡 |
| 数据 | **200–300 小时语音**（不需要文本、不需要标注），覆盖目标语言与音色 |
| 总机时 | **约 100–200 GPU·小时**（8 卡 ≈ 1–2 天；单卡 ≈ 1 周） |
| 第一个实验 | **8 GPU·小时** 的 S0 判据实验，决定后面 8 周值不值得投 |
| 最大风险 | **不是算力，是质量**：P2a 的 codes 一致率、vocoder 减重后的音质 |
| 失败的回退 | P2a 有 A/B/C 三档；vocoder 减重失败则整体停在 RTF 1.05–1.39 |

**一句话**：这不是一个大工程（算力上），但它有 3 个必须用耳朵和一致率把关的关口；
真正花时间的是**数据准备和听测**，不是训练本身。

## 1. 三个训练任务

| 任务 | 对象 | 参数量 | 改什么 | 产出 |
|---|---|---:|---|---|
| **T1 (P2a)** | code_predictor | 89 M | 16 次自回归前向 → 1 次前向 + 15 个并行头（注意力退化，5 层 transformer 塌成 5 层 FFN 塔） | 新 mmproj（含新 predictor 权重） |
| **T2 (P2b-1)** | code2wav 的 DAC 残差单元 | 118 M | 每个 DAC block 的残差单元 3 → 2 | 新 code2wav 权重 |
| **T3 (P2b-2)** | code2wav 通道 | 118 M | 768/384/192/96 → 640/320/160/80 | 新 code2wav 权重 |

T2 与 T3 共享同一套数据和训练脚本，**建议合并成一次训练**（先改结构再一起 recovery），
那样 T2+T3 只需一次 3–4 周，而不是两次。本文按合并后的 T2 计。

## 2. 数据

### 2.1 T1（predictor）

**只要 (talker hidden, 16 codes) 对，不需要文本、不需要标注。**

| 项 | 要求 |
|---|---|
| 内容 | 干净语音，24 kHz（会重采样到模型输入） |
| 时长 | **200 h 起**（≈ 900 万帧 @12.5 Hz）；100 h 可跑，但覆盖不足 |
| 语言 | 尽量覆盖要支持的 10 种语言；中文/英文各占大头 |
| 音色 | 必须包含目标音色（克隆场景的参考音、或 CustomVoice 的 9 个预置音色） |
| 来源 | 自建或可商用授权语料（M5 那边的门槛是 ≥100 h 可商用中文） |

**生成链路**（一次性，可并行）：

```
wav ──[Qwen3-TTS-Tokenizer-12Hz encoder]──> codes[T,16]
     └─[原 talker（0.6B，教师强制）]──────> hidden[T,1024]
保存 (hidden[t], codes[t]) 为 1 个样本
```

注意：我们现有的 GGUF 只有 tokenizer 的 **decoder**（code2wav）。
训练需要 **encoder**——它在 `Qwen3-TTS-Tokenizer-12Hz` 的 `model.safetensors` 里（我们下载过，encoder+decoder 合体 170 M），
不需要额外下载。

### 2.2 T2（vocoder，合并 T3）

**只要 (codes, wav) 对。**

| 项 | 要求 |
|---|---|
| 内容 | 干净、24 kHz、单声道、无背景音乐 |
| 时长 | **200–300 h**（vocoder 比 predictor 吃数据） |
| 与部署域一致 | 车载/客服等场景的噪声与语速要覆盖，否则上线后音色发飘 |
| codes | 由同一个 tokenizer encoder 产出（与部署时完全一致的码本） |

**关键**：T2 的输入 codes 必须来自**部署时那套 tokenizer**，否则 vocoder 学到的是另一套码本。

## 3. 算力估算（方法 + 数字）

估算方法：`FLOPs/样本 ≈ 3 × 2 × 参数量`（前向 2、反向 2，取 3 作总系数），
有效算力按 **150 TFLOP/s**（A100 bf16 理论 312，实际利用率 ~50%）。

### T1（predictor）

| 项 | 计算 | 结果 |
|---|---|---|
| 每帧前向+反向 | 3 × 2 × 89 M | 0.53 GFLOP |
| 每 epoch（900 万帧） | 0.53 G × 9 M | **4.8 PFLOP** |
| 每 epoch 时间 | 4.8 P / 150 T | **32 s**（纯算），实际含数据加载 ~5–8 min |
| 30 epoch | | **3–4 GPU·h** |
| 数据生成（200 h 语料跑教师） | | **3–6 GPU·h** |
| 评测/生成（每 epoch 出一次样本） | | 3–5 GPU·h |
| **T1 合计** | | **10–20 GPU·h** |

### T2（vocoder，合并 T3）

| 项 | 计算 | 结果 |
|---|---|---|
| 每秒音频前向 | 31 GMAC/s × 2 | 62 GFLOP |
| 每 epoch（200 h = 72 万秒） | 62 G × 720 k | 44.6 PFLOP |
| 加反向（×3） | | 134 PFLOP |
| 每 epoch 时间 | 134 P / 150 T | **15 min** |
| 100 epoch | | **25 GPU·h** |
| 判别器（多周期/多尺度，若用） | ×2 | 50 GPU·h |
| 评测/试听样本 | | 5 GPU·h |
| **T2 合计** | | **55–80 GPU·h** |

### 总计

| 阶段 | GPU·h | 8 卡墙钟 |
|---|---:|---:|
| S0 判据 | 8 | 1 h |
| T1 | 10–20 | 2–3 h |
| T2 | 55–80 | 7–10 h |
| 余量（重跑/调参 ×2） | 2× | — |
| **合计** | **~150–200** | **1–2 天（8 卡）/ 约 1 周（单卡）** |

**不确定性**：±2x。真正可能翻倍的是 T2 的迭代次数（音质不达标要重跑），不是 T1。

## 4. 分阶段计划（每个阶段都有 go/no-go）

### S0 判据实验（8 GPU·h，1 天）

**目的**：只回答一个问题——**"1 次前向的 predictor 能不能达到可用的 codes 一致率"**。

| 项 | 内容 |
|---|---|
| 数据 | 2000 帧（从语料里随机抽，够做一次快速评估） |
| 做法 | 用 1-pass 结构（15 个并行头）在 2000 帧上训到收敛（约 1–2 h），在留出集上算 codes top-1 一致率 |
| 判据 | **≥ 60% → 走 A 案（全并行）；50–60% → 走 B 案（2 次前向，8+7 分组）；< 50% → 走 C 案（蒸馏到 3 层 512 宽，保留 AR）** |
| 产出 | 一个数字，决定后面 8 周做哪一档 |

**这是整个计划里信息量最高的一次实验**：8 GPU·h 换一个 8 周的决策。

### S1：T1 正式训练（10–20 GPU·h）

| 项 | 内容 |
|---|---|
| 数据 | 200 h 的 (hidden, codes) 对 |
| 初始化 | 用原 predictor 的 v_proj/o_proj/mlp 热启动，15 个 head 用原 lm_head |
| 冻结 | talker、tokenizer、embedding 全冻 |
| 超参 | lr 1e-4 cosine，batch 512 帧，20–30 epoch |
| 产出 | 新 predictor 权重 → 写进 mmproj |
| 判据 | ① codes top-1 ≥ 60%；② 每个 codebook 熵 ≥ 教师的 80%（防坍缩）；③ 盲听 A/B MOS 差 < 0.2 |

### S2：T2 结构改造 + recovery（55–80 GPU·h）

| 项 | 内容 |
|---|---|
| 结构 | 残差单元 3 → 2；通道 768/384/192/96 → 640/320/160/80 |
| 初始化 | 未改动的层用原权重；被收窄的层用原权重切片（slicing）+ 少量噪声打破对称 |
| 数据 | 200–300 h 的 (codes, wav) |
| 训练 | 先冻结其余部分只训被改的层（10 epoch），再全量 finetune（40–80 epoch） |
| 判据 | ① PCM SNR（对原 vocoder）≥ 20 dB；② UTMOS/PESQ 不低于原模型 -0.2；③ 盲听 A/B 无明显退化 |

### S3：回归与打包（不需 GPU）

| 项 | 内容 |
|---|---|
| 导出 | 新权重按现有 converter 写进 mmproj（predictor 已是 `A_GEN_CODE_HEAD` 形状，vocoder 只是少一层） |
| 回归 | 用 [qwen3-tts-roofline.py](qwen3-tts-roofline.py) 与 [vocbench](../../../tools/tts/vocbench.cpp) 复测 RTF；确认与 §3 的预算一致 |
| 验收 | RTF ≤ 0.9、TTFA ≤ 1.5 s（预热后）、盲听通过 |

## 5. 评测体系（三层，缺一层都会翻车）

| 层 | 指标 | 门槛 | 工具 |
|---|---|---|---|
| 逐码 | codes top-1 一致率、每 codebook 熵 | ≥60% / ≥80% | 本仓库脚本（待写，10 行） |
| 波形 | PCM SNR、PESQ、UTMOS | ≥20 dB / 不低于原 -0.2 | 现成开源 |
| 主观 | 20 条盲听 A/B，MOS | 差 < 0.2 | 人工 |

**注意**：codes 一致率高但音质塌是 RVQ 的常见坑（靠后的 book 全变 0 也能有 60% 一致率），
所以第 2、3 层不能省。

## 6. 风险与回退阶梯

| 风险 | 概率 | 影响 | 回退 |
|---|---|---|---|
| S0 只有 50–60% | 中 | 改 B 案（2 次前向） | RTF 1.39 → 1.6 而不是 1.39 → 0.85（仍优于今天） |
| S0 < 50% | 低-中 | 改 C 案（蒸馏 3 层 512） | LM 收益从 -76% 降到 -40% |
| T1 音质退化 | 中 | 加"嵌入一致性"损失重跑 | 多 1 个 epoch 循环（+10 GPU·h） |
| T2 音质退化 | **高** | 只做 res 3→2，不做通道收窄；或退回 F16 | RTF 停在 1.05 |
| T2 完全不收敛 | 低 | 放弃 vocoder 改动 | RTF 停在 1.39（只有 P2a） |
| 数据不足 | 中 | 先用 100 h 跑 S0/S1，T2 等数据 | 按阶段推进，不阻塞 |

**最坏情况**：只拿到 P2a（10–20 GPU·h），RTF 1.39，仍是今天 3.74 的 2.7 倍改善。

## 7. 与部署的接口（训练产物怎么回到仓库）

| 产物 | 落点 | 运行时改动 |
|---|---|---|
| 新 predictor（15 并行头） | mmproj 的 `A_GEN_CODE_HEAD` + 新塔权重 | `qwen3tts-gen.cpp` 里把 `TTS_FAKE_NAR` 的分支转正（已写好，见 E22） |

## 8. 未验证 / 需要在有卡环境里确认的

1. 上面的 GPU·h 都是**估算**，实际要按 `samples/s` 实测校准（跑 10 分钟就知道）。
2. 2000 帧的 S0 是否足够代表整体（可能要 5000 帧，成本仍 < 1 GPU·h）。
3. T2 用不用判别器（用则 +50% 机时，但音质更容易保住）。
4. **tokenizer encoder 的推理速度没测成**。本机 `transformers` 是 4.41，而参考实现需要 >= 4.57
   （`ALL_ATTENTION_FUNCTIONS` 导入失败），装新版又会和 torch 2.3.1 冲突，所以没跑起来。
   数量级推算：encoder 与 decoder 同量级（decoder 在手机 CPU 上是 111 ms/帧 = 1.4x 实时），
   换到 GPU + 批处理大约快 10–30 倍 → **200 h 语料的编码约 10–30 GPU·h**，不是瓶颈。
   但这是推算，**数据准备阶段第一件事就是把它测准**（半小时的活）。
5. 若 T1 用 200 h 但其中中文只占一半，S0 的一致率可能高估（评测集要和部署分布一致）。

## 9. 关于"用 1.7B 蒸馏 0.6B"

这个问题要先拆成三件事，它们的答案完全不同。

### 9.1 用 1.7B 的 talker 当 0.6B predictor 的老师 —— 不可行

predictor 的输入是**本模型 talker 的 hidden**（0.6B 是 1024 维，1.7B 是 2048 维），
输出是**与这套 tokenizer 码本一致的 16 个 code**。
1.7B 的 predictor 是在 2048 维 hidden 上定义的条件分布，在 0.6B 的 hidden 上**没有定义**。
所以"换个更大的老师"在这里不是"更好"，而是"不成立"。

### 9.2 真正有用的蒸馏：P2a 内部的自蒸馏（KL 到原 AR predictor）

现在 P2a 的训练目标是**硬标签 CE**（对 tokenizer 产出的真值 codes）。
更有信息量的是**软标签**：把原 15 步 AR predictor 的**每步分布**当老师，训 1-pass 塔去逼近它。

| 项 | 硬标签 CE（现在的方案） | + KL 自蒸馏 |
|---|---|---|
| 老师 | 无（用真值 codes） | 原 AR predictor（15 步，权重已在手） |
| 额外成本 | — | 每步多一次 5 层前向（约 +1.5x 训练时间） |
| 预期收益 | 基线 | agreement 通常 +5–15 个点（软标签降低方差） |
| 实现 | 已有 | 训练时在线跑老师，取 15 个 head 的分布算 KL |

**为什么值得改**：S0 的判据是 60%/50% 两条线。如果 CE 只有 55% 而 CE+KL 能到 65%，
整个项目就从 B 案（分组 2 次前向）跳到 A 案（全并行），RTF 从 1.6 变 0.87。
**这 8~16 GPU·h 的差别决定后面 8 周做哪一档**，所以 S0 应该**两种都跑**（各 8 GPU·h）。

不建议把老师的分布存成文件：15 个 book × 2048 类 × 每帧 ≈ 123 KB/帧，200 h 要 100 TB。
在线跑老师是唯一可行的做法（老师只有 5 层，代价可控）。

### 9.3 用 1.7B 蒸馏整个 0.6B talker —— 可行，但那是"质量项目"，不是"速度项目"

如果意思是"用 1.7B 当老师，把 0.6B 的 talker 训得更像它"（text -> codes 的序列级蒸馏）：

| 项 | 数值 |
|---|---|
| 老师 | 1.7B talker（hidden 2048，参数量约 3x） |
| 学生 | 0.6B talker（28 层，440 M MAC/帧） |
| 数据 | **必须有文本**（当前 P2a 不需要）——200 h 语料要转写，或造合成文本 |
| 机时 | 学生前向+反向 3.6 GFLOP/帧，9 M 帧/epoch ≈ 32 PFLOP → 约 1–2 GPU·h/epoch；20 epoch ≈ **40–100 GPU·h**（含在线老师） |
| 收益 | 韵律/发音更像 1.7B，**RTF 一点不变**（学生的计算量没变） |
| 风险 | 1.7B 的采样本身有随机性，硬标签蒸馏会引入噪声；要用 KL 而不是 CE |

**它对本项目的价值是"预算转移"，不是"提速"**：

```
现在的等式：  质量(0.6B 原始) = 质量(蒸馏后) - 减重损失 - int8 损失
如果蒸馏后质量 > 原始，就多出一块预算，可以拿去换
   - vocoder 砍得更狠（res 3->2 再砍通道，甚至 3->1）
   - 或者 talker 上更低的位宽
```

但要注意量级：我们现在的质量缺口是 **int8 的 22.8 dB + 减重的 3.1 dB**，
而"蒸馏带来的质量提升"在 MOS 上通常是 0.1–0.3 分，**换不回 22.8 dB 那种量级的损失**。
所以它救不了 vocoder 的账，只能当"额外余量"。

### 9.4 结论

| 方案 | 建议 |
|---|---|
| 1.7B 当 predictor 老师 | ❌ 不可行（维度/分布不匹配） |
| **P2a 内做 KL 自蒸馏** | ✅ **已实现**（`training/qwen3tts/model_ar_teacher.py` + `train_predictor.py --kd`），零额外数据，可能直接把闸门从 B 案推到 A 案 |
| 1.7B 蒸馏 0.6B talker | ⏸ 先不做。要文本、40–100 GPU·h、只提质量不提速度；等 RTF 目标达成后再当"余量"来花 |

**顺序建议**：S0（CE 与 CE+KL 各 8 GPU·h）→ 按结果选 A/B/C → T1 → T2。
1.7B 蒸馏放在 T2 之后，如果那时音质还有余量、且你想再砍一刀 vocoder，再考虑。
