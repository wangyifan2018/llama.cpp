# Code Predictor 优化方案（QNN / A16W8，v81）

> 2026-11-22。现状：talker 用 A16W8 + ar1/ar32 双图共享权重；vocoder 静态图 A16W8；
> **瓶颈在 code predictor（CP）**。本文给 CP 的方案。

---

## 0. 结论

**把 CP 按 talker 的 ar1/ar32 那样做成 cp1 / cpN 双图（N=8..32）共享权重，跨帧批量。**

- 不需要重训，不改输出分布；
- 每帧带宽从 **615 MB 降到 19 MB**（N=32 时），按 v81 的 DDR 估算 **每帧 1-2 ms**；
- 延迟不增加（pipeline 本来就是按块流的，CP 只是从「每帧一次」变成「每块一次」）；
- 与 P2a（1-pass）**叠加**：批量先做，P2a 后做，两者互不冲突。

---

## 1. 为什么 CP 慢：带宽，不是算力

CP 每帧要跑 15 次串行前向，**每次都要把整份权重读一遍**：

    权重：约 89 M 参数，A16W8 下 w8 约 41 MB
    每帧：15 x 41 MB = 615 MB
    每帧算力：只有 15 x 78 M = 1.17 GMAC（约 0.1 ms 级）

**带宽是算力的几百倍。** 我们用 v73 实测验证过这个模型：

| 配置 | 每帧 | 说明 |
|---|---:|---|
| F16 权重 | 184.9 ms | 82 MB/步 |
| Q8 权重 | 84.5 ms | 41 MB/步，**字节减半、时间 x0.46** |

时间几乎线性于权重字节数 —— 这就是带宽受限的铁证。
所以换 NPU、换 HMX、换 QNN 都改变不了 `15 步` 这个乘法因子；能改的只有：
**让一次权重读取服务更多帧**（批量），或者**减少步数**（P2a）。

---

## 2. 关键前提：CP 的输出不回灌 talker

只要 talker 的下一步输入不依赖 CP 的 code1..15，**不同帧的 CP 彼此独立**，就可以批量。

我们的实现满足这一点：talker 每帧的输入是自身的 embd + pad（mtmd-helper-gen.cpp:359），
CP 的 15 个 code 只送 vocoder。既然你说 QNN pipeline 可以灵活改，建议按同样语义固定下来：
**talker 只吃 code0，CP 是纯旁路计算**。

（如果参考实现里有「16 码求和回灌 talker」的写法，必须去掉或改成 delay pattern，否则批量不成立。）

---

## 3. 图设计

### 3.1 两张图，共享权重

| 图 | 形状 | 用途 |
|---|---|---|
| cp1 | hidden [1,1024] -> codes [1,16] | 首块 / 尾块（不足 N 帧时） |
| cpN | hidden [N,1024] -> codes [N,16] | 常规块，N = 8/16/32 |

和 ar1/ar32 完全同构：同一份权重，两种 batch 形状。N 取多少取决于 DDR：
每帧带宽 = 15 x 41 MB / N，N=32 时 19 MB/帧，再大收益趋缓（计算开始占主导）。

### 3.2 图内结构（15 步在图内展开）

    输入： h[T, 1024]      （T = batch 帧数）
    步骤 g = 0..14：
      cur = proj_in(h)                                  # 第一步用 hidden，之后用上一步采样的 embedding
      5 层：attn_trivial(v_proj -> o_proj) + MLP          # 单位置注意力 = 恒等，q/k/rope/softmax 可删
      15 个头一次批乘：head[0..14] @ cur  ->  logits[T, 15, 2048]
      采样 -> codes[T, 15]（作为下一步的输入 embedding）
    输出： codes[T, 16]

注意：**这和 P2a 是同一张图的两种极端**。P2a 是「1 次前向出 15 个码」，
cpN 是「15 次前向、每次 N 行」。两者可以叠加为「1 次前向、N 行、出 N x 15 个码」。

### 3.3 采样放在哪

三个选择：

| 方案 | 做法 | 代价 |
|---|---|---|
| 图内 greedy | ArgMax（QNN 支持） | 最快，但分布变了 |
| 图内 top-k + 噪声 | QNN TopK 支持，输入一个随机张量 | 与你现在的 sampler 一致，推荐 |
| 图外采样 | 输出 logits[T,15,2048]，CPU 采 | T=32 时每块 3.9 MB 回传，约 0.2 ms，可接受 |

建议：**先图内 greedy 跑通性能**，确认收益后再换成 top-k（分布一致性要单独验，见 E28 的口径）。

---

## 4. 流水线改动

    现在（推测）： talker(帧) -> cp(帧) -> talker(帧+1) -> cp(帧+1) -> ... -> vocoder(块)
    改成：        talker x N -> cpN(N 帧) -> vocoder(块)

因为 pipeline 本来就是按块流的，**这一步不增加端到端延迟**（首块等满 N 帧是原有行为）。
唯一要处理的是首块：用小的 N（如 8）或 cp1，尾块不足 N 时用 cp1 补齐。

---

## 5. 预期收益（按带宽模型估）

| N | 每帧带宽 | v81 估算（20 GB/s） | v73 实测推算（6.3 GB/s） |
|---:|---:|---:|---:|
| 1（现状） | 615 MB | 31 ms | 97.7 ms（E36 实测） |
| 8 | 77 MB | 3.9 ms | 12.2 ms |
| 16 | 38 MB | 1.9 ms | 6.1 ms |
| 32 | 19 MB | **1.0 ms** | 3.1 ms |

算力上界（A16W8、NPU 有效 10 TOPS）：1.17 GMAC/帧 -> 0.12 ms/帧，**远低于带宽**，
所以 N=32 之后收益会变平（不再由带宽主导）。

---

## 6. 和 P2a 的关系

| 方案 | 步数 | 每帧带宽 | 需要重训 | 收益 |
|---|---:|---:|---|---|
| 现状 | 15 | 615 MB | - | - |
| **cpN 批量** | 15 | 615/N MB | **否** | 8-32x |
| P2a（1-pass） | 1 | 41 MB | 是（10-20 GPU·h） | 15x |
| **批量 + P2a** | 1 | 41/N MB | 是 | 最高 |

**顺序：先批量。** 它零风险、零训练，把 CP 从 31 ms 打到 1-4 ms；
做完之后 CP 很可能已不是瓶颈，P2a 就只剩「减少串行步数以缩短关键路径」的价值。

---

## 7. 在你们 QNN 上要验的清单

| # | 验什么 | 判据 |
|---|---|---|
| 1 | cpN 的图能不能编译（15 步展开 + TopK/ArgMax + 权重共享） | 能出 context binary |
| 2 | N=1/8/16/32 的每帧耗时 | 应接近 615/N MB 的带宽模型；偏离说明计算或调度成了主导 |
| 3 | 输出一致性：cp1 与 cpN 在同样输入下的 codes | 逐码一致（同 seed 的 greedy） |
| 4 | 端到端 RTF / TTFA | RTF 下降、TTFA 不退化 |
| 5 | 分布一致性（换 top-k 采样后） | 与基线逐码一致，或按 E28 的 sum(min(p,q)) 口径验收 |

---

## 8. 风险

1. **权重共享的编译约束**：QNN 的 context binary 中同一份权重被两张图引用，需要确认 converter 支持
   （你们的 ar1/ar32 已经做到了，所以这条路是通的）。
2. **静态 batch 带来的内存**：N=32 时激活约 32 x 1024 x 2 B x 若干层，几 MB 级，VTCM 放不下要走 DDR，
   需要在 converter 里确认 tiling。
3. **首块延迟**：N 取太大时首包变慢；用 cp1 + 小 N 的首块策略。
4. **分布一致性**：图内 greedy 会改变输出；要在切 top-k 之后复验。

## 9. 三个前提的确认结论（2026-11-22）

### 9.1 回灌：**不要回灌**，但要先用一句话验一次

结论：talker 只喂 code0，CP 的 code1..15 不回灌。这样帧与帧的 CP 完全独立，批量成立。

**语义陷阱**：如果原 checkpoint 是**按「16 码求和回灌」训练的**，去掉回灌会改变模型行为（音质/音色漂移），
那不是工程问题而是模型语义问题。我们这边的实现是 code0-only（talker 每帧输入 = 自身 embd + pad），
而且 E36 的 8 条中英文音频**全部被本地 ASR 正确转写**，说明 code0-only 语义自洽。

但他们那边如果是照参考实现导出的，**先花 10 分钟验一次**：同一条文本、同一个 seed，
分别导「回灌」与「不回灌」两条音频，比较 ASR 转写与 SNR/音色。一致就直接砍掉回灌。

### 9.2 权重共享：可以，但两张图必须用同一份量化权重

- cp1 与 cpN 共享同一份 w8 权重与同一套 encoding（ar1/ar32 已经证明可行）；
- 注意 batch 形状不同的图，**激活的 scale 可能不同**：A16 的 per-tensor scale 若按图分别标定，
  需要在 converter 里确认两张图共用同一组权重 encoding（重量化一次即可）。

### 9.3 采样：图内 top-k(50) + 噪声输入，先 greedy 跑性能

| 阶段 | 采样 | 目的 |
|---|---|---|
| 性能打通 | 图内 ArgMax | 验证 N 行批量是否接近带宽模型 |
| 上线 | 图内 TopK(50) + 一个噪声输入张量 | 与部署 sampler 一致；分布一致性按 E28 的口径验 |

不要用图外采样（回传 logits）：N=32 时每块 32x15x2048x4B = 3.9 MB，虽然只要 0.2 ms，
但会把 CP 从「一次图调用」变成「一次图调用 + 一次大回传」，破坏流水线。

### 9.4 由此定下的参数

| 项 | 取值 | 理由 |
|---|---|---|
| cpN 的 N | **32**（首块用 cp1 或 cp8） | 19 MB/帧 ≈ 1 ms；N>32 后计算开始主导 |
| 图内结构 | 15 步展开，每步 5 层 + 15 头批乘 | 无注意力、无 KV，图最简单 |
| 输入/输出 | hidden[32,1024] -> codes[32,16] | 静态形状 |
| 首块策略 | cp1 跑 1-8 帧，之后 cpN | 保 TTFA |

**批量后 CP 不需要 KV**（每帧单步只 attend 自己），这一点让它比 talker 的 ar1/ar32 还简单。

## 10. 给 v81 的实施建议（2026-11-23，基于 E48/E50 实测）

### 10.1 N 取多少

| 证据 | 结论 |
|---|---|
| M2：rows 8 之后 ms/帧 走平（6.04 -> 5.33 @ 32） | N=8 已吃掉大部分收益 |
| v73 CPU：rows 8 之后从 19.8 缓降到 16.4 | 同上 |
| v73 HTP：越宽越好，但 32 行仍慢于 CPU | 说明 HTP 的固定开销靠批量摊薄 |

**建议 N=8 起步，16 为上限**。v81 的 HTP+HMX 算力远高于 v73 的 HVX：
按 3000 GMAC/s 估，1.17 GMAC/帧 的算力下限是 **0.4 ms**，所以 N=8 时带宽（65/8 = 8 MB/帧 ≈ 0.4 ms @20GB/s）
和算力刚好平衡 —— **N=8 就够了，追 32 只多花内存**。

### 10.2 具体做法

1. **cp1 保首块**（TTFA），**cp8/cp16 跑常规块**；两张图共享同一份 w8 权重与同一套 encoding。
2. **不回灌**（talker 只吃 code0）——这是批量成立的前提（见 §9.1）。
3. **图内采样**：先 ArgMax 打通性能，再换 TopK(50)+噪声。
4. **批量不需要 KV**（每帧单步只 attend 自己），图里不要有隐式 state。

### 10.3 验收

| 项 | 判据 | 依据 |
|---|---|---|
| 每帧成本 | N=8 时相对 N=1 至少降 4 倍 | E48/E50 的曲线形状 |
| 等价性 | greedy 下逐码一致率 **>= 99.9%**（不是 bit-exact） | E49：15 步会放大浮点噪声 |
| 分布 | 采样下按 sum(min(p,q)) 口径，不比具体码 | E28 |
| 端到端 | RTF 下降、TTFA 不退化 | — |

### 10.4 在 v81 上先跑这个

```
./llama-mmabench -dev HTP0 -s 15 -r 5 -t 4
```

（我们已经在 v73 上跑过同一条命令，E50 有对照表。）看两件事：

- **rows=1 到 rows=8 的降幅**：v73 上是 3.7x（CPU）/ 6.1x（HTP）；v81 上应当更大（HMX 让宽矩阵更划算）；
- **rows=8 时的 ms/帧**：如果落在 0.5–2 ms 区间，说明 cp8 方案成立。

如果 v81 上 HTP 在 rows=1 就明显快于 CPU，那说明 HMX 已经在起作用，此时可以进一步考虑 cp1 也放 HTP。
