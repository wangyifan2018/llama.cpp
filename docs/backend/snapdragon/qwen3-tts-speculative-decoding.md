# Qwen3-TTS 投机解码方案（code predictor，v73）

> 调研时间 2026-11-22。已有两个实现做这件事，且其中一个的论文**就是 Qwen3-TTS + 端侧**：
> - NVIDIA **TensorRT Edge-LLM**：`CodePredictor Speculative Decoding`（已发布，单 flag 开启）
> - Argmax Inc. **arXiv 2609.37007**：RVQ position aware speculative decoding for on-device TTS（Qwen3-TTS 0.6B 实测）
>
> 本文把它们的机制、我们设备上的定量收益、以及在本仓库的实现路径讲清楚。
> 数字来源标注：【实测】= 本仓库 v73 上的测量（实验日志 E 编号）；【论文】= 上面两处；【推算】= 按模型算的。

## 0. 状态（2026-11-22 晚，已有 E28–E37 实测）

> 本文只保留**机制说明与成本模型**（§2–§4 没有被推翻），结论以那些实验为准。

已测到的关键数字（全部来自上面的实验目录）：

| 量 | 值 | 出处 |
|---|---|---|

本文 §4 的成本模型与 E28/E37 的实测一致（每多一行的边际成本、带宽主导），可以继续用来估新方案。

## 1. 现状：瓶颈在哪

| 段 | 每帧 | 调用次数 | 说明 |
|---|---:|---:|---|
| talker（28 层，code0） | 14 ms【实测 E15】 | 1 | 跨帧自回归，KV 增长 |
| **code_predictor（5 层，code1..15）** | **168–197 ms**【实测 E11/E13】 | **15** | 每步读一遍 82 MB 权重 |
| vocoder | 98–111 ms【实测 E21/E24】 | 1/chunk | 残差单元占 72% |
| 端到端 | 295 ms | | RTF 3.74 |

内层 15 次串行调用里，**每次只产 1 个 code，却要读完整份 82 MB 权重** —— 这正是投机解码要吃的浪费。

## 2. 两个已有实现的机制

### 2.1 TRT-Edge-LLM（零参数、链式）

- **draft 免费**：predictor 每个 RVQ 深度都有自己的 `lm_head`，且都读同一条残差流。
  深度 s 处持有 `h_s`，把 `head_{s+t}` 作用在 `h_s` 上，就是深度 s+t 的一个合法提议。
  **一个 GEMV 一个提议，没有任何新参数、不训练、不额外导出引擎。**
- **verify**：一轮跑一次 predictor 前向，覆盖"已提交位置 + N-1 个 draft 位置"。
- **accept**：标准拒绝采样 `min(1, p/q)`，首个拒绝处从 `norm(p-q)+` 重采样，全接受则给一个 bonus token。**分布严格不变**。
- 窗口 `--cp-spec-verify-size N`，有效范围 2–8，**接受率在 4 个深度之后饱和**，所以实用档位是 2–4。
- 限制：只做**链**（树需要专门 verifier kernel，未做）；greedy 下因 lm_head 应用方式不同可能与 AR 有细微差异，**采样下不变**。

### 2.2 Argmax 论文（+5×10⁻⁴ % 参数、树）

- 在 Medusa 上加两样东西：
  1. **RVQ position aware hidden offset** —— 给每个（深度，位置）一个极小的可学习偏移，修正"用 head_{s+t} 打 h_s"的系统性偏差；
  2. **稀疏树 attention mask** —— 让 drafter 和 verifier 融进**一次编译调用**。
- **实测 2.47 个接受 token/调用**，每轮开销 10–20%，200 → 88 次调用/秒，**2–2.2x**（iPhone 17 / MacBook M3）。
- 在 **top-k 采样下分布无损**，六语种 WER 持平。
- 论文明确否掉了 VADUSA/Nguyen（要训几百万参数 draft head、放宽接受规则改变分布）、EAGLE/ReDrafter（要新 draft 网络）、delay-pattern / masked parallel（要重训 backbone）。

**共同点**：draft 和 verify 融合成**一次**调用；接受率靠"免费头 + 极小的位置修正"就够，不需要第二个模型。

## 3. 为什么"免费 draft"在这里成立（结构上的原因）

predictor 的输出头是 `[n_embd, vocab, 15]` 的堆叠（本仓库 `A_GEN_CODE_HEAD`，conversion 里就是 `lm_head.{0..14}` 堆起来的），
每一步只用到其中一个 head，但**其余 14 个 head 同样接受这条残差流**。
所以"深度 s+t 的提议"= `head_{s+t}(h_s)`，代价是一次矩阵乘（2048×1024 = 2.1 M MAC ≈ 权重的 1/40）。

它的质量随 t 衰减 —— 因为中间那些 code 携带的新信息被忽略了 —— 这解释了为什么**接受率在 4 个深度附近饱和**。

## 4. 在我们设备上值多少（这是本文最重要的一节）

### 4.1 关键差别：苹果是"调用开销受限"，我们是"带宽受限"

论文的 2–2.2x 来自"把 15 次调用压成 ~6 次"：他们的每次调用开销（kernel launch、KV 管理）**不随行数增长**，
所以 6 次 ≈ 原来 15 次的 40%。

我们这边每次调用的成本 ≈ `R + (k-1)·C`：

| 符号 | 含义 | v73 实测值 |
|---|---|---:|
| R | 一次 1 行调用的成本（≈82 MB 权重读 + 1 行计算） | **10.5–13 ms**（168/16，或 1-pass 替身 13 ms） |
| C | 每多一行（verify 窗口加宽）的边际成本 | ≈ **2.6 ms**（78 M MAC @ ~30 GMAC/s，【推算】） |

于是总时间：

```
T(k) = (15 / A(k)) · (R + (k-1)·C)          A(k) = 窗口 k 时每轮接受的 code 数
```

用论文的接受率曲线（A(3)≈2.0、A(4)≈2.3、A(5)≈2.47）代入：

| 窗口 k | 每轮接受 A | 调用数 | 每调用 | 总时间 | 相对 168 ms |
|---:|---:|---:|---:|---:|---:|
| 1（现状） | 1.0 | 15 | 11.2 | **168 ms** | 1.00x |
| 2 | ~1.6【推算】 | 9.4 | 13.8 | 130 ms | 1.29x |
| 3 | ~2.0【论文】 | 7.5 | 16.4 | **123 ms** | **1.37x** |
| 4 | ~2.3【推算】 | 6.5 | 19.0 | 124 ms | 1.36x |
| 5 | 2.47【论文】 | 6.1 | 21.6 | 132 ms | 1.27x |

**结论：v73 上最优窗口是 3–4，收益 1.35–1.4x，不是 2.2x。**
再往上加宽窗口会被 C 吃掉 —— 因为我们每次调用本来就在读整份权重，加行只增加计算。

### 4.2 端到端意义

```
LM  = talker 14 + predictor 168 -> 14 + 123 = 137 ms
wall = max(LM, vocoder) = max(137, 111) = 137 ms   -> RTF 1.71
```

若同时把 talker/predictor 与 vocoder **并行**（现在还没做，是串行 295ms）：

```
RTF 3.74  --[SD, 不重训]-->  ~1.7
RTF 1.7   --[P2a, 要重训]-->  1.39（vocoder 决定）
RTF 1.39  --[vocoder 减重]--> 0.85–1.05
```

**所以 SD 是把 RTF 从 3.74 拉到 1.7 的那一步，成本和风险远低于重训**；
P2a 之后就只能再拿 0.3（因为 vocoder 变成硬地板），除非同时做 vocoder 减重。

### 4.3 为什么树形对我们特别值

窗口加宽的**字节成本为 0**（同一份 82 MB 只读一次），只有计算成本 C。
树形（4–8 个叶子的稀疏树）在同样的 82 MB 下能覆盖更多分支，
把 A 从 2.3 提到 3+ 的潜力比链式大 —— 而论文只做了链（树需要专门的 verifier kernel）。

**如果我们做，这可能是相对论文唯一能超过它的地方**（因为我们的带宽/计算比更极端）。

## 5. 三个方案

### 方案 A：免费头 + 链式（TRT 同款，零参数、零训练）

| 项 | 内容 |
|---|---|
| draft | `head_{s+t}(h_s)`，t=1..k-1，一次批乘 |
| verify | 一轮一次前向，k 行（前缀 + 新行），因果 mask |
| accept | 主机侧拒绝采样（top-k 支持），提交变长 |
| 收益 | **1.35–1.4x**（168 → ~123 ms）【推算，待实测】 |
| 工作量 | 图改造 + 采样逻辑，**约 1–1.5 周** |
| 风险 | 低。分布无损；greedy 下可能有末位差异（我们生产用采样） |

### 方案 B：位置感知 + 树（论文同款，+0.5 K 参数）

| 项 | 内容 |
|---|---|
| 在 A 之上加 | 每个（深度，位置）一个极小的可学习偏移；稀疏树 mask |
| 需要训练 | 只有那 0.5 K 参数（用**已有**的 (hidden, codes) 数据，几十分钟 GPU） |
| 收益 | 链式 A≈2.47；树形可能 3+ |
| 工作量 | A + 1 周 |
| 风险 | 中：树的 verifier 是新的 kernel 逻辑（论文也说这块要单独做） |

### 方案 C：与 1-pass predictor（P2a）混用

若 P2a 已训好，可用它当 drafter、原 AR 当 verifier → 接受率极高（drafter 直接给出 15 个 code），
但**如果 P2a 已经训好，就不需要 AR 链了**（除非要"无损"这个性质）。
所以 C 只有在"P2a 质量不达标、但想保留它做 draft"时才有意义 —— 属于兜底，不建议先做。

## 7. 实施计划

### P0（已完成，2026-11-22）：测接受率 —— 答案是否定的

**实测**：argmax 命中率 t=1 8.0%、t=2 0.2%；对齐扫描显示峰值在 p+2（7.7%）而不是 p+1，
即"用 stale hidden 加后一个 head"预测的其实是更靠后的 code，且强度远不够。
**A(2)=1.08 / A(3)=1.09 / A(4)=1.09，全部低于盈亏线 1.9。**

局限：这是 argmax 口径，不是严格的 `E[min(p,q)]`；后者在高熵码本上会更高一些，
但要从 8% 涨到 60% 不现实。**结论：方案 A 不投入。**

### P0 原始计划（留档）

不需要实现 SD，只要在**现有的 AR 图上**加一段诊断：
每一步 s，额外算 `head_{s+t}(h_s)`（t=1..3），与**真实采样的 code` 比对，统计
"t 步前向提议的 top-1 命中率"和"k 个提议里的最长正确前缀"。

产出：`A(2)/A(3)/A(4)` 三个数。**若 A(3) < 1.6，方案 A 收益 <1.2x，应放弃或直接上方案 B。**

> 这个诊断和论文的"位置感知"是同一件事的两面：先量出"免费头"的原始接受率，
> 再决定要不要那 0.5 K 参数去修正它。

### P1（1–1.5 周）：方案 A

1. `code_gen` 加 `verify(k)`：k 行前向 + 前缀因果 mask；
2. 主机侧 draft/accept/残差重采样；
3. 逐位比对：与现有 AR 路径在同一 seed 下**必须分布一致**（统计上）或**逐 code 一致**（greedy 时可能有末位差异，按论文的说明接受）；
4. 用 `TTS_TRACE` 量 `gen_code` 的调用数/总时长，验证 §4 的模型。

### P2（1 周）：方案 B 的位置偏移

在 P0 的数据上训那 0.5 K 参数，重测 A(k)；若 +0.3 以上再上树。

## 8. 门禁与风险

| 项 | 门槛 |
|---|---|
| A(3) | **≥ 1.8** 才做方案 A；≥2.2 才值得做方案 B |
| 分布 | top-k 采样下与基线**逐 code 一致**（同一 seed）；greedy 允许末位差异但要记录 |
| 音质 | WER 持平、盲听无差异（论文凭无损保证 + WER 持平验收） |
| 图开销 | 每轮 graph build 目前 ~1.4 ms；7 轮/帧 = 10 ms，若超过则要做图缓存 |

**最大风险不是算法，是"我们的采样器"**：现在的 top-k/top-p 在图上做，拒绝采样需要同一支撑集。
若处理不当，会得到"看起来对但分布变了"的结果 —— 这是这类工作最典型的坑。

| 顺序 | 项 | 收益 | 依据 | 工期 | 重训 |

| 0 | predictor 全主干 Q8（已完成） | 198.7 → **97.7 ms/帧**，RTF 3.93 → **2.68** | E35/E36 实测 | 已做 | 否 |
