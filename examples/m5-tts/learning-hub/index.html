01

认识被优化的对象：一帧音频是怎么来的

先把数据形状和计算图钉死，否则后面所有"优化"都是猜。

本章目标
  • 能画出 M5-TTS 的三阶段流水线，并说出每个张量的形状与单位
  • 理解 conditioning 序列为什么是"示范"，而不只是"条件"
  • 知道 llama.cpp 在这个工程里被复用了哪些原语、又绕开了哪些

1.1 三级火箭：backbone → depth → codec

把一段文本交给 M5，引擎先按标点切成若干段（每段 ≤80 字，总长 ≤2000 字），每段单独做一次 prefill：由控制标记、参考文本、目标文本、以及参考音频的 codec codes 拼成若干行 512 维 embedding， 一次性喂给 backbone。之后进入逐帧循环：backbone 走一步得到 hidden；depth 链用 15 次串行 decode 采出 16 个 code；codec 把攒够的若干帧解码成 PCM；next_hidden 再反馈给 backbone 开启下一帧。

与文本 LLM 的类比 prefill ↔ 读 prompt；逐帧 decode ↔ 逐 token decode；KV cache ↔ backbone 的上下文状态； sampler ↔ top-k 10 + 温度 0.9 + Gumbel-style 噪声采样；EOS ↔ 16 个 code 全 0（且前 6 帧禁止 EOS）。 不同点：LLM 一步采样 1 个 token，M5 一"步"要串行采 16 个 book，而且每个 book 的输入依赖上一个 book 的采样结果。

注意 voice.reference_text 与 input_text 之间没有分隔符，参考文本在前。 参考音频 codes 的每一行是 16 个 codebook embedding 的逐元素求和（row = code + 1 + book*2051， +1 因为 0 是 EOS）。换句话说：模型在 prompt 里同时看到了"这句话该说什么"和"用谁的声音、什么韵律说过一遍类似的话"。 这就是 in-context learning 式的音色条件，不是把说话人向量注入到某一层。

往下深挖 本章讲的是逻辑数据流。llama.cpp 在这条流水线里到底复用了哪些原语、 llama_batch.embd 这招"借壳"为什么成立，展开在 第 2 章 · llama.cpp 加速地图； 哪些模块真正在 HTP0、哪些在 CPU、一帧要跨多少次边界、以及为什么 App 形态拿不到 NPU， 统一放在 第 3 章 · HTP 后端：会话、批边界与硅的形状。

1.3 depth 链：16 个 book 为什么必须一个一个来

// m5_depth_heads.h: chain() 的骨架
proj(book0, hidden)  → logits[2051] → sample(T=0.9, top-k=10, noise=-log u) → code[0]
proj(projection, hidden) → projected_hidden
for book = 1..15:
    rows = (book==1) ? [projected_hidden, transform(code[0])] : [transform(code[book-1])]
    decoded = depth_decode(rows)          // 一次 llama_decode 调用，HTP 提交
    proj(book, decoded) → sample → code[book]     // 下一步的输入依赖这一步的采样结果
next_hidden = Σ_book audio_embedding[book][code[book]]   // 反馈给下一帧

权重布局（m5_depth_heads.h: layout()）：projection 块 16×2051×512 floats ≈ 67 MB（f32），projected 块 512×512， audio 块再来 16×2051×512。每帧要对 book 投影矩阵做 16 次 GEMV， 流式读取权重正是后面 f16 / int8 量化的用武之地。采样是 Gumbel 技巧： 噪声 n = -log(1-u) 由 JavaRandom LCG 生成，取 argmax(prob / noise)； 它要求按 book 顺序消耗随机数，因此"预生成噪声并向量化"也受到位精确约束。

本章要点 一帧 = 1 次 backbone decode + 15 次 depth 提交 + 16 次投影/采样 + 一批 codec 解码。 串行依赖有三层：book 内链、帧间 next_hidden、以及采样器随机数顺序。优化前先问：我要动的是哪一层依赖？
02

llama.cpp 是怎么做推理加速的

一个推理框架的加速手段，最后几乎都归到两个量上：这一步要搬多少字节，这条路要串多少次。这一章按瓶颈而不是按开关来组织 llama.cpp 的主要机制，最后回到本项目——我们借了哪几件。

本章目标
  • 能用 prefill / decode 两种瓶颈解释"量化为什么提速、又为什么提不了更多"
  • 说出全部加速手段其实只有四类：少搬字节、少走步数、少重算、少跨边界
  • 看到一个旋钮或参数，先判断它在你的形状下应当有效还是无效，再去量

2.1 两个阶段，两种瓶颈

任何自回归生成都被切成两段：prefill（一次吃进 prompt 的 T 行）和 decode（一次进 1 行）。 这两段的成本结构完全不同，llama.cpp 的加速手段基本也是分别针对它们设计的。

先算一笔算术强度的账。一个 N 参数的模型，每处理一个 token 要做约 2N 次浮点乘加， 读一遍约 N × bpw / 8 字节的权重（bpw = bits per weight）：

prefill（T 行）： 算术强度 ≈ 2NT / (N·bpw/8) = 16T / bpw   ← 随 T 增长
decode（1 行）：  算术强度 ≈ 2N  / (N·bpw/8) = 16 / bpw    ← 与模型大小无关

于是：prefill 是算力题，decode 是带宽题。这不是定性说法，在 llama.cpp 自带的 benchmark 里能直接读出来：同一份 tools/quantize/README.md 的 Llama-3.1-8B 数据， 体积砍到 1/5、prefill 只掉 15%，decode 却涨了 2.74 倍。

三个读数值得停一下：

  • prefill 基本不受量化影响（923 → 784，−15%）。它不是带宽受限的，砍字节对它帮助很小。
  • decode 的收益在逐档衰减：兑现率 85% → 70% → 65% → 43%。低比特 kernel 要做更多解码工作 （两级 scale、码本查表），有效带宽从 468 掉到 253 GB/s。"体积减半 ⇒ 时间减半"只在第一档近似成立。
  • 这就是第 11 章那个"模型砍掉一半、时间没动"的通用版本。我们当时的 backbone Q4_0 实验体积 −48%、 时间 −3%（兑现率 ≈ 3%），不是意外，是这条曲线的延长线。

2.2 权重怎么变小：块量化家族

量化的做法一句话说完：把每 32 个（或 256 个）权重切成一块，用低位整数存，每块存一个 scale 把整数映射回浮点。 三代格式的差别，全在"scale 怎么存、块多大、误差往哪分配"。

一个容易忽略的约束：能产出 ≠ 能加速 llama-quantize 能生成十几种格式，但每个后端只实现了其中一部分的 vec_dot。 没实现就退回通用路径：文件变小了，时间反而更长。选量化格式的正确顺序是 先看目标后端支持哪些类型 → 再在这些类型里挑 bpw，不是反过来。 本项目只有 Q8_0 / Q4_0 可选，因为 HTP 侧的 mul_mat 只覆盖这两类（第 6 章 6.1 节）。

2.3 CPU 上真正发生的事

"量化权重 × 浮点激活"听起来要么慢（要反量化），要么不准。实际做法是把激活也量化： mul_mat 里先把 src1 按行 from_float 成 Q8_0（type_traits_cpu[type].vec_dot_type）， 再做整数点积，最后用 scale 乘回浮点。所以整条路径是 int8 × int8 → int32 → ×scale， 没有"逐权重反量化再乘"这一步。

围绕这个内核，CPU 侧还有两个容易被忽略的机制：

  • repack（权重重排）。加载时把 Q4_0 权重从"行优先"重排成 4×4 / 4×8 / 8×8 的交错布局， 让一条 NEON 指令同时吃 4–8 行权重。选择逻辑在 ggml/src/ggml-cpu/repack.cpp： NEON+dotprod → q4_0_4x4；NEON+i8mm → q4_0_4x8；AVX2 或 SVE → q4_0_8x8， 同时要求输出维数能被 4 / 8 整除。同样的比特数，换个内存布局就能快一倍；--no-repack 可关掉做对照。
  • 线程池与 barrier。每个算子都要在 n_threads 个线程之间分块、同步、再继续（ggml_barrier）。 线程多了，同步开销和内存竞争会吃掉收益——所以 decode 的线程数存在一个"甜点"。

这个甜点在 llama-bench 的数据里非常清楚（7B Q4_0，纯 CPU）：

顺带一句：Arm 把手写的微内核库 KleidiAI 开源之后，llama.cpp 以可选 CPU 后端的形式把它接了进来 （ggml/src/ggml-cpu/kleidiai/）。它不改变算法，只把 i8mm / dotprod 那条路径的常数项压下去—— 这正是"有效带宽 468 → 253 GB/s"那段差距的现实来源之一。

2.4 图与调度：跨后端边界的运输成本

ggml 是"先描述、再执行"：一次 decode 先把全部算子写成 ggml_cgraph，再由 ggml_backend_sched 决定每个算子在哪块设备上跑。关键在于它会把图切成若干段： 张量在哪个 buffer 上，算子就归哪个后端；跨后端的那一刀，要在边界处把输入张量 copy 过去 （ggml_backend_sched_split_graph 为每个 split 记 i_start / i_end / n_inputs， 逐个 copy）。

所以"多 offload 一层就快一点"是错觉。每多切一刀就多一次 copy + 一次同步，-ngl 的最优点 在"这一段搬到快设备上省下的时间 > 边界运输成本"处；层数扫参就是在找这个拐点。

还有一个推论：图的形状会改变成本。attention 要读多少行 K/V，是写进图形状里的： batch 大，边界搬的字节多、但每次搬运摊到的计算也多；batch=1，边界便宜，可每层收益也小。 第 11 章的 KV pad 实验（n_kv 从 256 压到 32）改的就是"图里多读多少行被掩蔽的 K/V"—— 机制一样，只是对象从"跨设备拷贝"换成了"跨 cache 行的读取"。

2.5 状态复用：KV cache 的四个层级

自回归的第二次生成不必从零算起，这是 llama.cpp 最值钱的一层抽象。KV cache 是一个按位置索引的 K/V 行数组， 所有复用都是对它的增删查改。由浅到深有四级：

  1. 请求内（天然）：decode 只算新行，旧行的 K/V 直接读。
  2. 跨请求前缀：新请求开头和上一次相同，就只算不同的部分。CLI 侧是 --prompt-cache， server 侧是 slot 复用 + --cache-reuse。收益 = 省掉的行数 × 每行成本， 所以长系统提示、固定音色前缀、多轮对话的收益最大。
  3. 降精度：-ctk/-ctv 把 KV 存成 Q8_0 / Q4_0 / IQ4_NL。但有个硬约束： V 量化要求 Flash Attention 开着，否则直接报错（src/llama-context.cpp： "quantized V cache was requested, but this requires Flash Attention"）。原因是 FA 的 kernel 直接在量化 V 上做加权求和，非 FA 路径得先反量化，那还不如不省。
  4. 窗口与检查点：滑窗注意力模型（SWA）用 --swa-full / --ctx-checkpoints 在"只留窗口"和"整段重算"之间取折中，本质是把"重算"换成"存快照"。

把 KV 的成本写成式子，就能判断该不该降精度：

每 token 的 KV 字节 = 2 × n_layer × n_kv_head × head_dim × bpw / 8
# 例：32 层、8 个 KV head（GQA）、head_dim 128、上下文 4k 行
F16 → 2 × 32 × 8 × 128 × 2 B = 131 KB/行 → 4k 行 = 512 MB
Q8  →                        65 KB/行 → 4k 行 = 256 MB

算完再决定：如果 KV 只有几十 MB（比如本项目的 depth 上下文 256 行），降精度省下的内存换不来速度， 反而把数值风险引进来了——所以我们保持 F32。

2.6 减少步数：投机解码家族

decode 慢的根源是"一次只出一个 token"，而一次前向处理 k 行和 1 行的成本几乎一样（都是读一遍权重）。 投机解码就是利用这一点：先快速猜出 k 个 token，再用一次前向并行验证它们，接受最长的正确前缀。

llama.cpp 里这条路已经长成一个家族，按"草稿从哪来"分成两类：

类型（--spec-type）草稿从哪来要额外模型什么时候值得
draft-simple一个同族小模型（-md 指定）要有小模型且领域接近；最通用的一档
draft-eagle3单层 draft，读主模型的 hidden state要（专用 draft）接受率最高的一档，用显存换速度
draft-mtp模型自带的多 token 预测头模型内含训练时就带 MTP 的模型，白捡
draft-dflash / dspark / dflash2块扩散：一次出一个整块要想"一次出多 token"且对 GPU 友好
ngram-*（5 种）从上下文里抄 n-gram不要输出高度重复：改代码、格式化、引用原文

最后一行常被忽略却最便宜：不用模型也能投机。只要输出大概率复述输入（代码补全、RAG 引用、格式化）， 直接从上下文取 n-gram 当草稿，r ≈ 0，只要 α > 0 就是白赚。

同一个技巧，换一个依赖结构就失效 本项目的 depth 链每帧要走 15 步，看起来正是投机的目标。但它有三个前提全不成立： ① 15 步是同一帧内串行，不是"往后预测 token"；② 每步的输入是上一步采样出来的结果， 不是已知前缀，没法"先猜 k 个再一次验证"；③ 我们训过草稿头，α 上界只有 0.18，而门槛（α > r）是 0.72。 接受率不是工程问题，是"两个分布有多像"的问题——这就是日志 §14 把这条路判死的原因（第 12 章还会提到）。

2.7 决策树：先量什么，再拧哪个

把上面五节压成一次判断。顺序不能反——先分阶段，再选杠杆；先量占比，再谈收益。

03

HTP 后端：会话、批边界与这块硅的形状

"模型跑在 NPU 上"这句话对 M5-TTS 只对了一小半。它没说清哪条路径每帧都在走、哪条一辈子只走一次；也没说清这块 NPU 有几个向量单元、多少片上内存、能不能做矩阵乘。这一章把 HTP 后端拆到可以自己复算的程度。

本章目标
  • 分清「建立会话」与「提交一批算子」是两条完全不同的路径：前者每进程一次，后者每帧 15 次
  • 把一次提交拆成固定项 F 与每行项 R，并说明为什么优化目标是减少批边界，而不是减少函数调用
  • 记住这块硅的硬形状——2 个 HVX 128B 单元、2 MB VTCM、无 HMX——以及它如何决定权重布局与设备分工
  • 用张量形状、内核覆盖和边界成本解释 backbone、depth、heads、codec 的归属，并复述一帧 15 次往返的结构

3.1 会话不是提交：两条路径

先纠一个最常见的误读：把"每帧 15 次提交"想成 15 次 FastRPC 调用。FastRPC 确实在链路上， 但它承担的是建立会话，不是每帧的提交。这两件事的代价差三个数量级，混在一起就会得出完全错误的优化方向。

两条路径的区别不止在快慢，还在谁在等谁。会话建立是同步 RPC：宿主线程阻塞到 DSP 返回， 中途失败就是一个错误码。批提交是异步的：dspqueue_write 只把门铃按下去， 宿主立刻回来继续写下一批描述符，直到需要结果时才 dspqueue_read。 这个异步性决定了后面所有结构——两个进程能各自排自己的队、codec 能在 CPU 上与 depth 重叠、 以及"取消一个请求"必须自己实现（没有可中断的同步调用可打）。

3.2 一次提交的真实粒度：opbatch

一次提交 = 一个 opbatch。宿主把这次要跑的 N 个算子写成一串描述符（buffer 表、tensor 表、 op 表）放进共享内存的固定槽里，默认 8 个槽轮转，单批最多 2048 个算子； 门铃里只带一个 24 B 的头（序号 + 四个计数）加一个指向槽的描述符。DSP 侧拿到槽以后，按图 3-1 第二条路径的流程处理， 期间不回到宿主。

所以"提交"这个字在 HTP 上指的是批边界，而批边界的工作量与批内算子数几乎无关： 两次全量 dcache flush、一次 L2 预取、一次工作队列唤醒与收尾。 depth_batch_bench 就是为拆开这两项写的：同样处理 28 行，用不同次数提交。

这个模型立刻给出两个可以证伪的推论，而且都用已有实验验过了：

  • 批越大越划算。把 15 步合成 1 批，应该能省掉 14 个 F（约 17.5 ms/帧）。 但 depth 第 b+1 步的输入依赖第 b 步的采样结果——宿主必须先看到 logits 才能构造下一行， 所以这条链无法合并（第 5 章把这件事算成结构天花板）。
  • R 不是权重带宽。若 R 由 DDR 带宽主导，把 depth 权重从 Q4_0 10.7 MB 换成 Q8_0 21 MB 应该让 R 接近翻倍。实测只慢 9%。说明 R 的主体是 HVX 计算与每行的固定开销， 权重带宽不是主项——这也是"把 depth 量化到更低比特"被判死的依据（第 6 章）。

OPFUSION 是同一机制的另一半：把 RMSNorm+Mul、MatMul+Add、SwiGLU 这类三段式 在批内合成一个算子的一个 opcode，省的是批内算子数与中间张量的往返访存。 实测关掉它只慢 5%（14×2：44.7 vs 42.6 ms）——depth 图本来就小，能省的有限。 反过来说：如果一个后端开了融合也拿不到 10%，说明瓶颈不在批内。

3.3 这块硅的形状：2 HVX、2 MB VTCM、没有 HMX

3.4 权重为什么要重排：tile 不是压缩

权重进 DSP 之前会被重排成 32×32 的 tile。条件写在 htp_is_tiled_weight_tensor 里： 第一维是 32 的倍数、连续、不是 view、第四维为 1。F16 到 Q4_0 到 Q6_K 都在覆盖范围内，每种类型有自己的 tile 字节数。

关键事实：重排不改变总字节数。Q4_0 的一个 tile 是 576 B = 32 行 × 16 B 的 nibbles + 32 个 fp16 的 scale（64 B）；而 ggml 行主序下 32 行 × 32 个权重也是 32 × 18 = 576 B。 Q8_0 的 1088 B 同理（1024 + 64）。所以它不是量化、不是压缩，纯粹是换个顺序摆。

把 3.3 和 3.4 放一起，就能推出一个容易被忽略的结论：在这块硅上，"量化更狠"的收益路径和别处不同。 没有 HMX、VTCM 只有 2 MB，意味着算子是"流式读 tile + 向量乘加"，而 R 又被实测证明不是带宽主导—— 于是降低比特数省下的是 DDR 流量，却换不来多少时间（第 6 章会看到 Q4_0 → Q8_0 区间只有 9%）。

3.5 从计算图推导 CPU / HTP 的分工

现在把后端机制放回模型。真正跑在 HTP0 上的只有两个 transformer： backbone（8 层 Q8_0，32 MB）与 depth core（5 层 Q4_0，10.7 MB），合计约 43 MB 权重常驻。 heads 投影、采样、噪声生成、codec 声码器、PCM 输出全在 CPU。

下面沿着一帧音频看各段的输入形状、算子与状态，再用实验检查分工是否划算。 实测限定在本项目的 SM6650、Hexagon v73、无可用 HMX 路径及当时的 GGML/ORT 构建。

Backbone：让一串投影和注意力共用一次设备执行

前缀 [N, 512] 或单帧输入 [1, 512]
  → 8 层：RMSNorm → Q/K/V 投影 → RoPE + KV 注意力 → 输出投影
             + 残差 → RMSNorm → SwiGLU FFN + 残差
  → hidden[512] → CPU 上的首码本预测

权重以 Q8_0 常驻后端，KV 随语句累积。前缀阶段的投影可处理多行；逐帧 decode 的投影更接近矩阵向量乘。 HTP 的价值来自支持这些形状的 HVX 内核，以及多层在同一后端执行、只为整张图付一次批边界。 不能从 GEMM 峰值推断单行收益。同机初测中，32 行 prefill 的 CPU / HTP 中位数约 70.2 / 73.9 ms， 7 次 decode 约 281.6 / 87.7 ms；CPU 样本有波动，这组对照只涵盖 backbone。 详见移植笔记：SM6650 同机 backbone 初测。

这组数字正是 3.2 节模型的形状：prefill 有 32 行，摊薄了批边界，HTP 与 4 核 CPU 打平； decode 每次只有 1 行，CPU 每行都要重走一遍算子调度，HTP 把整图化成一次提交，7 行共用一份开销，于是差出 3 倍。

生产通常按首块 2 帧、后续 4 帧执行。在码本时间轴上，新数据很短；上采样后，4 帧对应 4 × 1920 = 7680 个采样位置，尾部在高时间分辨率上连续做卷积和激活。 发布版 ONNX 的静态图包含 31 个 Conv、85 个 MatMul、8 个 Softmax 和 29 个 m5::Snake， 还有两百多个 DequantizeLinear。这些数字来自发布版文件的静态统计。 ORT 在加载图后仍可消除或融合节点，运行时实际耗时要看 profile。

  1. 内核覆盖。生产图已经把反卷积改写成 MatMul 加布局变换，并以 QDQ 描述部分量化算子。 能执行 MatMul 只覆盖了其中一类形状。尾部的空洞卷积、逐点 Snake、切片和缓存更新也需要匹配的数据类型、 布局及实现。该设备的 HTP 探针拒绝所测形状的直卷积与通用 Sin；ORT CPU 可以连续执行这些操作， 并使用融合 Snake。
  2. 切图位置。4 帧码本只有 64 个索引；把一个尾部卷积单独迁移时，边界经过的是放大后的浮点激活。 以 96 通道、7680 个输出位置为例，FP32 输出约 2.81 MiB；完全物化 im2col 的逻辑张量为 7680 × (96 × 7) × 4 字节，约 19.7 MiB。这是展开空间的估算，不能当成实际传输字节或 DRAM 流量。 端到端测量还要计入重排、提交、同步和读回。

3.6 一帧内的 15 次跨边界往返

引擎 ↔ stage 一行 FP32 512 维 = 2 KB。默认 --depth-pipe 下，每个 book 都要 「CPU 构造 transform 行 → 送 HTP0 跑一步 depth core → 回 CPU 投影 2051 类 → 采样」，一帧 15 次。 --depth-chain 能把整条链搬进 stage、pipe 往返从 15 次降到 1 次，但实测打平 （depth 4.15 vs 4.08 s，逐位一致）；m5_ring 共享内存反而更慢。 用 3.2 节的模型解释就很直接：chain 省掉的是 pipe 往返，并没有减少 HTP 侧的批边界—— 每一步仍然要等采样结果才能构造下一步输入，15 个 opbatch 一个都免不了。

3.7 旋钮：为什么 OPPOLL 的收益随形状变

把 3.2 节的表按开关分组看（图 3-2），OPPOLL 的效果很反常：28 次提交的场景差 84%， 14 次差 63%，只有 1 次时只差 17%。额外成本随批次数增长，却不随行数增长—— 这与"计算变慢"无关，是"两次批之间跨了一个睡眠/唤醒"。

机制在代码里只有一行：等结果时 dspqueue_read 的超时。默认给一个长超时， 宿主线程睡下去等 DSP 通知；OPPOLL=1 把超时设成 0，变成自旋。 在单请求 CLI 里这条差得惊人（同句 RTF 1.62 → 0.75）；在常驻 server 里它只值 18% （同一请求墙钟 7.47 → 6.34 s），而且 CPU 秒数几乎不变（30.2–31.5）、四份 WAV 逐字节相同。 这正是它的性质：省的是调度延迟，不是算力。也解释了为什么它能被写进部署脚本而当成"免费收益"。

3.8 三个容易被读错的现象

两个 HTP 会话 ≠ 两个 NPU

都是 HTP0，只是两个独立的 llama 上下文（各自 KV、各自量化、各自一份 VTCM 预留）。它们分时复用同一物理 DSP，所以"两路并发"不是翻倍，而是排队。

App 形态拿不到 HTP

OS 对 app uid 封了 /dev/adsprpc-smd（EACCES），JNI 版只能全 CPU 跑（RTF ~0.79–0.90）。只有 shell 域启动的 m5-server 才能用 NPU——所以全书的 NPU 结论都只适用于 server 形态。

耗时正常但结果全零

3.3 节那个 HMX bug 的形态：能力位报错 → 内核选了不存在的路径 → 输出全零，而耗时看着完全合理。所以 NPU 的验收必须有数值门禁，"能跑完"不等于"跑对了"。

由此决定的一个工程结构 backbone 与 depth 被拆成两个常驻子进程，不是为了"并行"，而是两个边界条件逼出来的： 会话建立（打开 skel、预留 VTCM、建队导出）是每进程一次的成本，不能进任何一帧的预算—— 冷启动首包 0.398 s 里就含这一段；并且一旦 DSP 侧崩溃，进程级隔离才不会把整个 server 带走。 先量清楚启动成本与崩溃域，再决定进程拓扑——这是端侧推理里最容易被忽略的一层设计。
本章要点 这一章只讲了三件事，但它们决定了后面所有的账。
第一，提交的粒度是批不是调用。会话建立每进程一次，批边界每批一次，成本 F ≈ 1.25 ms 与批内算子数无关； 每行 R ≈ 0.91 ms 且不是权重带宽。所以"减少往返次数"和"减少批边界"是两笔完全不同的账—— --depth-chain 打平正是因为它只动了前者。
第二，硅的形状先于代码。2 个 HVX 单元定了并行度上限，2 MB VTCM 定了"权重只能流式"， 没有 HMX 定了"别用 GEMM 峰值做推理"。这三条一起把量化收益压成了个位数百分比， 也把 codec 留在了 CPU。
第三，能力位要自己查。后端替你做的那份猜测可能给出全零结果和一个正常的耗时。 数值门禁不是质量流程的装饰，它是 NPU 上唯一能发现这类错误的探针。

4.1 RTF 的定义与三个陷阱

RTF = 生成耗时 ÷ 生成音频时长。小于 1 表示"比实时快"。它直观、便于对比，但有三个坑：

  1. 短句惩罚：模型有固定的 prefill / codec 预热 / 首批调度成本，音频越短摊不掉。实测 7 字句 RTF 0.918，19 字 0.837，24 字 0.742——同一份代码，只因为句子长度不同。
  2. 热漂移：连续压测让 SoC 升温，同一代码 RTF 从 0.75 慢慢漂到 0.87、0.91。跨轮绝对值不可比，必须同轮交替 A/B（A→B→A→B）。
  3. 口径不一致：CLI 单次进程 vs server 常驻进程、wav 全量 vs pcm 流式、是否包含首次 codec prime，都会改变分子。
可迁移的做法 拿到一条耗时曲线，先做线性拟合：T(N) = 固定开销 + 每单位成本 × N。 截距指向冷启动 / prefill / 图初始化，斜率指向真正的逐 token（逐帧）热路径。 优化截距只对短请求有意义，优化斜率才对长请求有意义——两者 often 需要完全不同的手段。

4.5 案例：一次"提速后音质变差"的完整调查

这一节是 4.3 分层门禁的实战版。Serena 换上 Flash Attention 融合内核后，个别字出现疑似破音。 调查分四步，每步只回答一个问题：

  1. 复现并保住基线。 同一文本、音色、种子重新生成，两份产物都保留。听感是验收条件，RTF 只描述吞吐。
  2. 按算子形状拆 profile。 按 DSP 批次形状分组、只比较同形状的 decode（旧 profile 里 1,820 个 80 算子批次）： FP32 普通注意力 ≈ 2.65 ms/decode，FP16 普通 ≈ 2.60–2.65，FP16 Flash ≈ 1.92——先确认 Flash 真的走了 HVX，提速是真的。
  3. 把"生成"与"解码"隔离。 分别保存基线与 Flash 的 codes：同一 attention 配置跨 codec 的 codes 完全一致， 排除 PCM16 削顶与分块边界——问题出在生成轨迹，不在声码器。
  4. 同一组 codes 盲听定位。 INT8 版比 FP32 版更明显：量化边界放大了轨迹差异，但轨迹本身已经变了。
人耳证据与判决 三条文本各两份、a/b 顺序打乱的双盲试听：用户指出第 3 组（车站播报）的 3a 差——揭晓后 3a 正是融合内核版。 KV 精度没变、codes 之外的客观指标全对，但只换 attention 实现也能被听出来。 按 4.3 节等价性分层判决：第 ③ 层不通过即否决，与第 ①② 层通过与否无关。 样本量小（3 组、1 组被指出），所以结论是"不进入生产"，不是"所有文本都能听出差异"—— 分层门禁的价值恰恰在于：它规定了哪一层有一票否决权。
音质验收 ≠ 性能验收

两条链路分开走：性能看 elapsed_s 与每帧成本；音质看 codes 一致性 → ASR → 盲听。任何"客观指标全对"都不能替代最后一层。

归因一次只动一个变量

6.1 f16：一个"优化了但根本没编译进去"的故事

depth heads 每帧要做 16 次 512×2051 的 GEMV，权重是流式读取的。 最初的 f16 内核守卫写成了 GCC 风格宏 __ARM_FEATURE_FP16，而 NDK clang 19 实际定义的是 __ARM_FEATURE_FP16_VECTOR_ARITHMETIC / __ARM_FEATURE_FP16_FML。 结果宏从未匹配、f16 是死代码，而构建日志与一次 objdump 检查都误报"已生效"，于是留下"RTF 持平"的假象。

修复动作有两步：改对宏名，并在 CMakeLists 里全局加 -march=armv8.2-a+fp16+fp16fml； 验证方式是反汇编数指令（确认 128 条 fmlal 真的出现），再做同种子交替 A/B： 每帧 57.3 → 48.3 ms（-16%），5/5 测试句 RTF 改善 11~13%。

教训 编译期优化必须以产物为准（反汇编 / 符号 / 计时），不能以构建日志或"代码写对了"为准。 宏名要按实际编译器的特性宏写；跨平台 SIMD 路径尤其容易静默回退到标量实现。

6.2 heads int8：带宽减半，heads 快 2.5 倍

埋点显示 heads 每帧约 13.4 ms，而每帧要流过约 34 MB f16 权重（投影 + projected 块）， 折算带宽约 2.5 GB/s —— 这是典型的内存带宽瓶颈，算力几乎没参与。 于是做 per-row 对称量化：每行 512 个 float 求 max|w|，scale = max/127， 存成 int8 + 一个 float scale；GEMV 用 NEON 把 int8 解包后以 f32 累加，最后乘回 scale。 注意 只量化权重、输入仍保持 f32，避免激活量化的误差叠加。

量化还带来一个必须讲清楚的现象：codes 从第 2 帧起翻转 ~90%。别急着判死刑——见下面这张图。

6.3 什么时候量化必须被否决：backbone Q4_0

用 host 端 llama-quantize --allow-requantize 把 backbone 从 Q8_0(32.4 MB) 压到 Q4_0(17.1 MB)， 同轮交替 A/B 的数据很漂亮：backbone_s 0.632 → 0.495（-21%），depth 也因 DDR 竞争减少快了 15%， 两版 ASR 全对。但音频时长从 5.90 s 缩到 4.94 s（-16%，语速变快）——这是韵律漂移。 人工试听后决定保持 Q8_0：TTS 的自然度优先于这部分 RTF，且 backbone 只占墙钟约 14%。

方法论 ASR 检查的是"说了什么"，韵律检查的是"怎么说"。生成式任务的指标天然偏向内容， 凡是改动会影响采样分布的优化，都要有感知层验收（这里是人耳；图像任务里是视觉检查/感知指标）。 同时要算清收益占比：为了 14% 的环节去牺牲全局听感，通常不划算。

6.5 小结：怎么判断"该不该量化"

  1. 先测流量与耗时是否成比例（改权重的位宽做 A/B），确认是带宽瓶颈；
  2. 若是，优先量化流式读取的大权重块，且尽量只量化权重、保留激活精度；
  3. 用首帧一致性 + ASR + 感知验收三层门禁，别用逐位 codes 当标准；
  4. 算清该环节在总墙钟的占比，收益天花板 = 占比 × 提速比例；
  5. 如果环节被流水线重叠隐藏（codec），现在优化它不会反映在端到端 RTF 上——等主瓶颈降下来再做。

8.4 方法论

  1. 温度要作为协变量记录，否则「变慢」永远无法归因；判漂移用 ms/帧，别用 RTF。
  2. 历史漂移先复现再当问题：复现失败就写清环境，而不是继续在模型里找原因。
  3. 产品路径与调优路径必须同参：所有 CLI 实验是 (2,4)、线上是 (4,16)，「线上 0.78 vs CLI 0.71」被当成口径差解释了好几轮，实际是配置差。
  4. 配置税是真实存在的优化项：它不在模型里也不在 kernel 里，但值 10%。每换一次基线，就该重扫一遍「当初为了让 A 变快而选的 B」。
Q1　温度涨了 15 K，为什么每帧耗时一点没变？
因为没跨过降频阈值。这次峰值只有 52 °C（DSP 55.6 °C），而典型 throttle 在 80–95 °C；同时 shell_front 只有 31–34 °C，说明整机（后盖、边框）在吸收热量，SoC 的结温远没有到需要降频的程度。另一个原因是热时间常数：单次合成 4 s、间隔 0.1 s，8 分钟只够把温度抬 15 K，还没到稳态。「温度升高」和「性能下降」之间隔着一条阈值线，中间还有 DVFS 的调整空间；判断有没有降频要看每帧耗时或实际频率，不能看温度本身。
Q2　codec 从 2.47 s 降到 2.25 s（−9%），墙钟为什么反而慢了 11%？
因为 codec 在 max() 的非瓶颈侧。批次从 4 帧加到 16 帧，每次 ONNX 调用的固定开销被摊薄，codec 自身确实快了；但 16 帧意味着 codec 每次要连续工作约 640 ms，而这期间 depth 已经产出下一批并进入等待，流水线出现空转。于是「省下来的 codec 时间」没有变成墙钟，反而因为等待和批次边界损失了更多。这和「codec 单独 −20% 收益为 0」是同一条规律的加强版：有时候它不只是 0，还会变成负数。

并发与有效算力：8 核为什么不等于 8 倍

上一章把「同一台机器、同一份代码」跑出了 10% 的差距。这一章换个问法：如果同时来两个用户呢？直觉是「8 核，两台机器都撑得住」。实测是：能接，但几乎不能并行——多开一个实例只换来 6.6% 的吞吐，代价是延迟翻倍。

本章目标
  • 会用「一个请求的 CPU-秒」判断一台设备能装几路
  • 理解 8 核为什么只有约 4.4 核的有效算力
  • 知道并发之后 max() 的哪一侧会翻转，以及为什么吞吐只涨 6.6%

9.2 三种并发形态

9.4 最重要的一课：max() 的那一侧会翻转

把两种场景的公式并排写出来，就能看到一件容易被忽略的事：

算术 单请求：wall = 0.61 + max(depth 2.80, codec 2.44) + 0.09 = 3.61 → 瓶颈是 depth
并行：wall = 0.74 + max(depth 5.45, codec 5.93) + 0.09 = 6.76 → 瓶颈变成 codec

于是：想靠「降 depth 50%」拿收益，单请求是 0（被 max() 吃掉），并行也是 0（此时 codec 是瓶颈，depth 降到 2.73 也无用）。反过来想靠「codec 移出 CPU」拿收益，单请求是 0，并行也只有 +15%（因为 depth 的 5.45 接棒成为瓶颈）。

两侧必须同批改造，否则两侧都是 0。这是「捆绑」的第三次独立验证——第一次来自成本模型，第二次来自并发实测，这一次来自「瓶颈侧会随场景翻转」。

9.5 方法论：这一轮我错了四次

本章的结论来得不干净，前三次测量全是错的。记下来因为比结论更有用：

  1. 孤儿进程。第一次测出「单实例 481 秒 CPU」。原因是之前 SIGKILL 的脚本留下了 stage 常驻进程，加上 Android App（com.m5.offline）的两个 CPU 模式 stage 还在跑——它们的进程名被改写成 libbackbone_resident.so，pidof backbone-resident 抓不到。测量前先 kill -9 并 ps 确认清零。
  2. 拿 CLI 当被测对象。CLI 每次启动都要初始化 ORT session（141 MB ONNX），墙钟 6.4 s 里有 2.1 s 是启动，于是「每请求 25 CPU-秒」虚高一倍多。要测稳态成本，必须用常驻 server。
  3. 相信裸 wait。nohup ./m5-server & 是同一个 shell 的后台作业，裸 wait 会连它一起等，脚本永远不返回。要 wait $p1 $p2。
  4. 把调频滞后当成热漂移。静置后第一批请求慢 44%（3.60 → 5.19 s），我一度以为是热。实际是 walt 把大核压到 633 MHz 后升频滞后。含义：任何 A/B 必须先跑一次 discard 请求把频率拉起来，否则第一组必然吃亏。
Q3　既然 8 核只用 6 核，为什么不能再塞第三路？
因为「6.06 核」是平均占用，不是「还剩 2 核空闲」。第一，8 核里有 5 个是 595–633 MHz 的低频核，按 2.2 GHz 归一后总有效算力只有 4.4 核，而 6.06 这个数字本身就是按核数算的平均，对应的频率加权占用更高。第二，并行时 codec 已经从 2.44 s 退化到 5.93 s，说明它已经在争抢；再塞一路只会让退化倍率继续上升，而不是线性分摊。第三，两路时 depth 已经 5.45 s（1.94×），第三路会是 2.9×——HTP 的分时是硬约束。判断能不能再塞，别看核数，看「瓶颈侧当前的倍率」：倍率已经 >2 就不是加资源能解决的。
Q4　为什么省掉 codec 的 72% CPU，只换来 15% 吞吐？
因为省掉的资源要用来「解锁」另一侧，而不是直接变成时间。并行时墙钟是 0.74 + max(depth 5.45, codec 5.93) + 0.09。假设 codec 完全不占 CPU 也不占 HTP，max() 立刻由 depth 的 5.45 决定，墙钟降到 6.28 s——从 6.76 到 6.28 就是 6.6%→15% 的全部收益。想再多，就必须同时把 depth 也降下来，此时墙钟才会跟着 max() 一起掉。优化一个被 max() 遮住的分支，最多只能拿回「另一侧的时间」；想突破，必须动另一侧。
10

性能分析方法：从分项计时到决策

前面十章讲的是「这个模型怎么加速」。这一章把过程中反复用到的判断方式抽出来：它们不依赖 M5-TTS，换一个推理引擎、换一块 NPU 也成立。核心只有一句——先算清楚这个优化能兑现多少，再决定要不要动手。

本章目标
  • 能把「试过，没收益」升级成「有机制解释的判死」，并写清复活条件
  • 掌握十条速查判据与四个反复出现的陷阱
  • 会用「斜率 / 截距 + 隔离开关」把固定成本拆开（0.398 s 首包案例）

10.1 为什么先建模型

分项统计（backbone_s / depth_s / codec_s）本身不是模型，把它们的结构关系写出来才是。本项目的两条分支并行重叠，所以墙钟是 backbone + max(depth, codec) + 固定开销，不是三者相加。用残差检验：不同配置下减出来的固定项都约 0.197 s，说明模型抓住了结构。有了它，动刀之前就能算出「codec 降 20% 值多少」——在日志 §13 的答案是 0，在日志 §16 的答案仍是 0。省下的是一整轮无用的量化实验。

10.2 十条速查判据

  1. 先写可证伪的墙钟模型，用它算可兑现收益，不要用单项耗时当目标。
  2. 区分「组件变快」与「端到端变快」；max() 结构下优化非瓶颈分支收益为 0。
  3. 每次成功优化后重算余量、重排优先级：KV32 把 25% 余量吃到 1.15%，旧结论立即失效。
  4. 同轮正逆序交替 A/B，固定文本与 seed、取中位数；判据是 elapsed_s。热漂移能让同代码 RTF 从 0.75 变 0.91。
  5. RTF 只在输出不变时可用。分母 audio_s 会随生成轨迹变化，必须同时看墙钟、每帧成本、输出长度。
  6. 等价性分层：① codes/WAV 逐字节；② ASR + 音频统计；③ 多文本人耳盲听。heads int8 与 B/Q4 都证明「指标全对 ≠ 听感通过」。
  7. 归因实验一次只改一个变量（KV 精度 × kernel 实现），并用 profile 数算子证明改动真的生效，别靠 env 名猜。
  8. 算子形状比墙钟推测更接近机制：SOFT_MAX 256:32:8:1 直接解释融合 kernel 为何只剩 7%。
  9. 负结果写清机制与复活条件：α 上界 0.18、反压是固定税、可预测性沿链衰减、kernel 改变轨迹。
  10. 先做便宜的判死实验，再投入训练或改图。960 帧离线数据判死草稿，16 次合成判死 Flash 线。

10.3 四个反复出现的陷阱

分母会变

flash-f32 的 RTF 从 0.700 降到 0.666，看似快 5%；实际帧数 69→76、音频长 10.5%、墙钟 +5.1%。只看 RTF 会得到完全相反的结论。

只看单边指标

--threads 3、chunk (2,4)、OPPOLL=1 都是按「codec 单独耗时」「首包最短」定的。日志 §13 用端到端墙钟重扫 48 次，没有任何配置快于默认。

把近似当等价

codes 分叉、帧数漂移时，两条轨迹已经不是同一个任务；此时比速度没有意义，先过门禁再谈性能。

沿用旧基线

「Flash 是最大杠杆（-17%）」在 KV32 之前成立；转正后它只剩 ~0.9%。每条结论都要带上它的基线。

冷 / 热口径混用

CLI 每次都是新进程，codec prime 缓存必然空；常驻 server 同音色第二次起就命中，首包差约 0.08 s。之前所有分项实验用 CLI，报的都是冷启动数。延迟必须标明是「重启后首次」还是「稳态」。

10.4 把负结果变成资产

日志 §12–§14、§17 四条线全部判死，但留下的是可复用的机制：α 上界、固定税、可预测性衰减、kernel 轨迹漂移。写清楚「为什么不行」和「什么条件下复活」，比记录「试过没收益」有价值得多——它让下一个人不必重跑一遍，也让自己不会在换基线后重复投入。

10.5 案例：把 0.398 s 首包拆开

稳态 RTF 被 max() 锁死（日志 §16），但首包由固定项主导，是另一本账。扫 --first 1/2/3/4/6/8 两轮交替，拟合出 first_pcm = 0.234 s + 74.6 ms/帧（残差 <21 ms）；斜率恰好等于 depth 单帧 31.7 ms 加 codec 单帧 40 ms。再用 --no-overlap 把并行项暴露：codec prime 0.230 s、backbone prefill 0.190 s，overlap 下取 max，所以固定项其实是 codec prime，不是 prefill。斜率/截距加隔离开关，比逐个埋点更省事。

Codec::restore_prime 按参考 codes 的最后 8 帧缓存 codec 递归状态，命中就跳过那 0.23 s。查出的问题是缓存条件错配：warmup 用的是 voice 0（官方样例），而 Web 默认 Serena，于是每个用户的第一次请求都在给用不到的音色付冷启动。部署层加一个 --voice serena 让默认音色对齐，首次 pcm 从 0.346 降到 0.280 s（wav 0.507→0.420），零引擎改动、稳态不退化。先查缓存命中条件，往往比写更快的 kernel 更划算。

那次优化留了个尾巴：prime 缓存是单条目，换音色立即失效（切回仍要 0.49 s）。下一节把这条最后的冷启动路径关掉，并顺带说明一个极易算错的账：被跳过的操作值 0.23 s，实际能省下的只有约 0.04 s。命中路径仍要发送 32 行共享 prefix——实测只值 2–4 ms（见第 11.4 节），协议改动已判死；--first 2 --chunk 4 已是最优，别再试更小的首块。

Q5　某候选把 RTF 从 0.700 降到 0.666，能上线吗？
不能只看这个数。本例中帧数 69→76，音频 5.32→5.88 s，墙钟 3.724→3.914 s（+5.1%），RTF 下降纯粹因为分母变长。而且四条文本/seed 的 codes 与 WAV 全部不一致，已经不是同一个任务。正确顺序：先看过没过等价性门禁（逐字节 → ASR → 盲听），再看 elapsed_s 与每帧成本，最后才算 RTF。这个候选是日志 §17 的 flash-f32，结论是判死。
Q6　把首块从 2 帧减到 1 帧，首包为什么反而从 0.398 s 涨到 0.616 s？
因为 kTail = 2400 个样本大于单帧 kHop = 1920：第一个 chunk 的输出被全部留作 overlap tail，drop = 0，根本没有 PCM 写出。首包只能等第二个 chunk（4 帧），等于等 5 帧——0.234 + 5 × 0.0746 = 0.607 s，与实测 0.616 s 吻合。减小批次不一定降低延迟，要先看输出阈值。另外把 prime 的输出接进 tail 虽然能让 1 帧发出声音，但会把参考音色原声混进开头，不能这么修。

10.6 案例：把单条目缓存换成 LRU，以及「跳过 ≠ 省下」

日志 §19 留下的冷启动尾巴，改法只有约 25 行：把 prime_codes_ / prime_inputs_ / prime_offset_ 换成 vector<PrimeEntry>，命中移到 front、新条目插 front、超出容量裁尾。关键是 key 取「真正决定状态的最小输入」——这里就是参考 codes 的最后 8 帧，而不是音色名字或索引。于是换文本不失效、同名不同内容不误命中，浏览器内联的临时音色（请求里带 codes）也自动纳入同一缓存。容量 4、每条目 1.04 MB，约 4.4 MB 上限；M5_PRIME_CACHE=1 复现旧行为、=0 禁用缓存，M5_PRIME_STATS=1 打印 hit/miss/save。

怎么验收：容量按 0,1,4,4,1,0 交替重启 server，每轮固定序列「serena → 官方样例 → serena → 官方样例 → serena → pcm」，共 36 次请求。服务端日志给出的 prime 调用统计是 0/13、8/13、11/13 次命中：容量 4 多出的 3 次正好是三个「切回音色」请求。切回三请求首包中位数 0.500 → 0.463 s（-7.5%）；用永远冷的 cap=0 轮做热漂移基线（s1→s3 +0.032 s）校正后，单条目的冷启动惩罚 +0.044 s 被压到 +0.005 s。更硬的门禁是 30 份 WAV 跨容量、跨冷热、跨 6 次重启全部同一哈希；用 6 个不同的内联临时音色逼出 LRU 驱逐，被驱逐后重算的两个音色哈希也与首次完全相同。

Key 取最小决定输入

prime 状态是 8 帧 codes 的纯函数，就别用音色名字当 key。缓存语义由被缓存的计算决定，不由请求身份决定。

先让缓存可观测

hit/miss/save 日志比「首包看起来快了」可靠得多；它还能给出每条目字节数，让容量选择有依据。

禁用缓存一物两用

cap=0 既是「命中省多少」的冷基线，又是同轮热漂移的校正量——不必另跑一轮漂移实验。

等价性跨命中状态

不只验证「同配置两次一样」，要覆盖冷、热、驱逐后重算、不同容量、不同进程；否则缓存可能悄悄改变输出。

Q7　缓存命中跳过了一个 0.23 s 的操作，首包为什么只快了约 0.04 s？
因为 prime 与 backbone prefill 并行：冷启动固定项是 max(0.230, 0.190) = 0.234 s，命中后 prime 消失，固定项退化成 prefill 的 0.190 s，省下的只是两者差值约 0.044 s（pcm 路径实测 0.058 s）。稳态章节里 max(depth, codec) 让「codec 单独 -33%」收益为零，是同一个结构在首包维度的翻版。算收益要重画并行结构，不能拿组件耗时直接相减；同理，也不要因为收益比预估小就判定优化无效——它仍然消除了换音色时用户能感知的那一次卡顿。
从实验开关到编译期默认 一个优化从"实验室里快"走到"生产里快"，中间还有三步：①转成编译期默认（KV pad 32 写进 get_n_kv()，M5_KV_PAD=256 可回退；backbone 分支显式保留 256，严格复现实验条件）、 ②部署脚本去掉特殊目录与 env 注入（顺带补上缺失的 stage 库推送）、 ③交替 A/B 复验（默认 3.775 s vs pad 256 4.163 s，12 次 codes 与 WAV 哈希全部相同）。 没有第 ③ 步的转正都是赌博：改的是默认值，赌的是每一个还没跑过的输入。
Q8　既然 codec 有 25% 的空闲余量，为什么"让 codec 少干点活、把 CPU 让给 depth"没用？
因为 depth 的成本主体花在 HTP0 的 15 次提交（F≈1.25 ms/次 + R≈0.91 ms/行），不是 CPU 争抢。实测把 ORT 线程从 3 降到 2 会让 codec 慢 25%，而 depth_s 反而略升；chunk 从 4 加到 16 让 codec 快 7%，depth_s 几乎不动。 并发反压确实存在（关 overlap 后 depth 快 11.3%），但它是"codec 线程存在"的固定税，不是负载强度的函数；而 overlap 本身净赚 43.9%，这笔税必须付。
11

余量重估：串行项与 max() 的另一面

第 10 章教会你「非瓶颈分支的收益恒为 0」。但这句话有个前提：你要先知道哪个分支在瓶颈上。基线一旦改变（这里是把 depth 的 KV 读取范围从 256 缩到 32、又把 prime 缓存换成 LRU），瓶颈就换人了，昨天的结论今天就过期。这一章讲的是转正之后必须做的第二件事：重算收益矩阵，并用最便宜的手段验证它。

本章目标
  • 能分清三个「推理时间」口径，知道做决策该用哪一个
  • 能把分项耗时映射回成本模型，判断一项改动落在加法项还是 max 分支
  • 理解为什么单边优化归零、为什么在当前估算中优先优化 depth，再处理 codec

本章三个实验都在「不改模型图、不重训」的前提下完成，结果是一正两负。价值不在那个正的 2.3%，而在两次负结果各自留下的可复用判据。

11.1 先分清三个「推理时间」

问「还有没有优化空间」之前，必须先定口径。这三条账的分子分母都不同，混着谈会得出互相矛盾的结论：

口径当前值主导项约束
稳态墙钟 / RTF（69 帧长句）3.70 s / 0.694max(depth, codec)并行天花板，单侧优化归零
首包（pcm，命中）0.28 s固定 0.190 + 2 帧 × 74.6 ms不受 max() 约束
短句 RTF（≤7 字）常 >0.9固定项摊不薄与长句不是同一张账

稳态那条账的残酷之处在于两条轨道几乎完美平衡（2.853 vs 2.820，差 1.15%）。这是最坏的优化局面：你花力气把 depth 降 20%，codec 立刻变成新瓶颈，墙钟几乎不动。反过来，只要有一项不在 max() 里，它就值得优先动手。

11.2 串行项：唯一能 100% 兑现的那 0.677 s

backbone_s 在公式里是加法项，占墙钟约 18%。它不在瓶颈上，所以「降 10% 得 10%」在这里成立——这是全流程唯一还有这种性质的计算项。剩下的候选手段只有两类：

  1. KV 读取宽度（pad）：零重编译、开关现成，门禁是逐字节等价，成本最低。
  2. 中间档量化 / 分层混合精度：Q6_K、Q5_K 或前后层保 Q8，在 Q8 与 Q4 之间找音质拐点；一次把 Q4 试过头导致音频短 16%、韵律漂移被否掉，所以必须盲听。

先做第 1 项。历史上 backbone 的 pad 被硬编码成 256，原因很朴素——当初做 depth KV32 实验时要求「其他条件严格不变」。于是这个开关从没被单独测过。命令行的 --backbone 参数会整体替换 stage 启动命令，加个 M5_KV_PAD=128 前缀就能只注入 backbone 子进程（depth 仍是 32），一行代码都不用改。

11.3 「修好缺陷」不等于「拿到收益」

回到首包那条加法账。--first 1 一直有个众所周知的毛病：单帧 chunk 只有 1920 个样本，而 write_chunk 要把最后 kTail=2400 个样本留作下一块的 overlap 缓冲——全被扣住，一帧根本发不出声音，首包只能等第二个 chunk（共 5 帧，0.575 s）。

修法很直接：加一个 M5_FIRST_TAIL，让首个 emit chunk 少扣或不扣 tail。缺陷确实修好了，但收益是负的：

四个可迁移的点：

看斜率项归属哪一侧

首包 74.6 ms/帧 ≈ depth 31.7 + codec 40，是相加。改 --first 只动 depth 那一半，codec 的单帧调用固定开销却涨了——一侧省、另一侧还。

11.4 先测占比，再谈改协议

prime 命中时可以跳过 codec prime，但引擎仍然把 32 行共享 prefix 发给 backbone stage——因为协议是「先发 header 再发两块矩阵」，少发一块需要改协议。省 64 KB 听起来值得改，先量一下：

sh=32 rs=71–85  hdr=0.1ms  shared=1.3–3.4ms  rest=7–12ms  wait=85–101ms  total≈105ms
m5-stage prefix hit sh=32 discard_ms=2.2–4.3

32 行（64 KB）的传输加丢弃只要 2–4 ms：占 prefill 往返（约 105 ms）的 3%，占命中首包（0.41 s）的 不到 1%。大头是 wait 段，也就是 backbone 对 rest 行做的真实 decode——那是算力，不是搬运。

算一下风险收益：省 2–4 ms，换一次管道错位崩溃的可能（这条协议以前踩过，错配时 stage 会读垃圾 header）。不成比例，直接判死。更重要的是它留下一条判据：凡是「优化传输」的提案，先问它在端到端里占几个百分点；单看「省了一半数据量」没有意义。

11.5 量化：把模型砍掉一半，为什么时间没动

backbone 剩下的候选只有「降精度」了。直觉上：Q8 31 MB → Q4 16 MB，每帧少读一半权重，该快。实测不是——五组权重精度、三轮交替，backbone 一动不动：

为什么不吃带宽？把 backbone_s 拆开看：0.687 s ≈ prefill 0.19 s + 69 帧 × 7.2 ms。每帧只送 1 行（hidden 512）进去，8 层权重 Q8 约 13 MB，摊到 7.2 ms 上只有约 1.9 GB/s——远低于这块 LPDDR5X 的可用带宽。反过来算：每层约 0.86 ms、每层约 9 个算子，即 每算子 0.1 ms，正好是 NPU 的 dispatch / 同步固定成本。69 次「1 行 decode」= 69 次独立调用，成本由调用次数决定，不由权重字节数决定。

这次实验还附赠两个必须记住的坑。第一，所有量化都改变了输出：帧数 69 → 71/73/74，音频 5.32 → 5.48/5.64/5.72 s（长 3~7.5%）。分层混合（首末层保 Q8）也没救回来，帧数反而最多。第二，因此 RTF 全部「变好」（0.702 → 0.685），而墙钟全部变慢（+2.2~5.5%）——分母又被做大了，这是同一个陷阱的第三次出现。

判死 backbone 中间档量化（Q6_K / Q5_K_M）与分层混合精度在端到端上一律负收益，且都以韵律漂移为代价。复活条件只有一个：先让 69 次单行 decode 不再是 69 次独立调用（改图合并、或降低每层 dispatch 成本），单次调用变大后带宽才会重新成为限制——先改调用形状，再谈精度。

11.7 方法论补充

  1. 转正后立刻重算矩阵：KV32 转正让 depth 不再是瓶颈，「间接加速 depth」的历史收益（Q4 曾 −18%）换基线后只剩 −4.6%。旧数字必须带上它的基线。
  2. 在等价收益里挑最保守的配置：pad 32/64/128 差异在噪声内时选 128，因为它图重建次数减半，长句更稳。
  3. append 模式的 dump 是 A/B 地雷：--dump-codes 用追加写，冒烟轮与正式轮共用同名 tag 会静默叠加，产出假性 SHA 不一致（WAV 是截断写，不受影响，且 sha256sum 输出里 wav 在前）。A/B 脚本每轮先 rm -rf 结果目录，冒烟用独立 tag。
  4. 测量类实验别改会崩的代码：分段计时加一次对照就能定案，不必为 2–4 ms 去动协议。
  5. 「模型变小」≠「变快」：先判断受限类型。判别实验只要两档极端值（Q8 对 Q4，体积差 2×）；2× 体积差换不来时间，就说明不是带宽问题，别逐档试精度。
  6. 分层的价值前提是「有收益可分」：mix4 这种边缘层保精度的做法，只在量化本身能加速时才有意义；加速为 0 时它只是「更慢 + 输出不一样」。
  7. 先做零成本的那一个：本章第一项零重编译、门禁现成，跑 16 次就拿到 −2.3%；另外两项各花了半天证明不该做——判死也是产出。
Q9　backbone 只占墙钟 18%，为什么优化它比优化占 77% 的 depth+codec 更划算？
因为它们在墙钟公式里的位置不同。depth 与 codec 并行，墙钟取 max(2.853, 2.820)，两者只差 1.15%——把其中一侧降 20%，另一侧立刻成为新瓶颈，端到端收益约 0。backbone 是加法项：wall = backbone + max(...) + 固定，它降 7.7%，墙钟就真降约 7.7% 的那一份（实测 −2.3% 墙钟，符合 18% × 7.7% 量级）。判断优化价值不是看谁耗时最长，而是看它在公式里能不能兑现。这也解释了为什么「先降 depth」在 KV32 之前是对的、之后就不再是。
Q10　`--first 1` 从「等 5 帧」修成「1 帧就出声」，为什么首包仍不如 `--first 2`？
因为首包的成本是 depth 与 codec 相加而不是取 max（流水线还没填满）。--first 1 让 depth 少跑一帧（约 −31.7 ms，加上后续调度约 −75 ms），但 codec 要为一个 chunk 单独调用一次，单帧调用的固定开销让 codec_s 从 2.77 涨到 2.87 s，多花约 80 ms，两者抵消。实测 0.401 vs 0.387 s。要让它转正，得先把 codec 的单次调用开销降下来——所以这个开关的价值不是「现在能用」，而是把复活条件写清楚，等 codec 捆绑改造落地后只需重跑一次。

11.8 真实一帧，与"两版数字"的教训

2026-11-15 03:31 的实跑请求（Serena，87 帧）：墙钟 5.281 s、RTF 0.770、首包 0.561 s；分项 backbone 0.734 / depth 4.160 / codec 3.156 s，折合每帧 8.4 / 47.8 / 36.3 ms。

把结构变成判据 wall ≈ backbone + max(depth, codec) + prefill。两条分支一旦接近， 任何单边优化都会被 max() 吃掉：codec 变快而 depth 不变，墙钟一动不动； depth 变快到 codec 以下，codec 立刻变成新瓶颈。这比"哪个模块慢就优化哪个"的直觉重要得多。
后来修正（台账 §30） 上面写的"两条轨道只差 1.15%"来自日志 §25 的斜率外推（41.3 vs 40.9 ms/帧）； 日志 §29 的进程族记账给出的段实测是 40.6 / 35.4 ms/帧——差 13%。这一版数字改写了台阶的起点： depth 减到 codec 以下时，先有约 0.36 s 的空档是白送的，因此 P2（depth 重训）单独可兑现 −10% 而不是 0。 斜率拟合适合回答"再多一帧要多久"，段实测才适合回答"哪一侧在瓶颈上"。 两版数字都留在这里，正是为了示范：结论要跟着测量口径走，而不是跟着记忆走。

11.9 depth 与 codec 联合重训的收益估算

免重训的手段全部穷尽后，收益矩阵只剩一条路：让两侧一起降。数学上很直白—— wall = 0.874 + max(depth, codec)，要端到端降 δ，两侧都必须 ≤ (1−δ)×现状； 单边改进要么被 max() 吃掉，要么只吃到两侧差距那一小截。这就是"捆绑"的含义： depth 重训（把 15 步压成 2 步）与 codec 收窄必须同批立项，按当前假设，建议顺序为 P2 → P3 → P2'。

门槛不在模型，在数据 P2 需要 ≈100 h 可商用语料（2.25 M 帧训练样本 + 教师逐 book logits），P3 需要 50 h； 官方三条样例（约 20 s）不能用于训练。没有语料这不是"做得慢"是"做不了"—— 这一条应该在讨论任何模型细节之前先确认。
决策（2026-11-15） 单路 RTF 0.68 已满足实时、首包 0.26 s 与它无关——P2+P3 卖的是并发（CPU 10.6 → ≈7.2 秒/请求， 单机 2–3 路才装得下）与功耗，不是"更快"。触发立项的三个条件：产品要多路、功耗受限、 且已有语料。都不满足时，正确动作是把"单机 1 路 + 2 路限流"写进产品文档。 计划、门禁与 kill 判据的完整版在台账 §30。

12.3 性能问题诊断模板（可直接抄）

  1. 锁定口径：固定输入、固定种子、设备冷却到同一状态；记录 RTF、墙钟、首包、帧数。
  2. 画泳道：把 prefill / 主 decode / 辅助解码 / I/O 画在时间线上，标出哪些重叠、哪些串行。
  3. 拟合：T(N) = 截距 + 斜率 × N；截距归冷启动，斜率归热路径。
  4. 分类瓶颈：改字节数（带宽）、改调用次数（提交）、改并发（竞争）、改输入长度（依赖），一次只动一个变量。
  5. 算天花板：该环节占墙钟百分之几 × 最多提速几倍。占比 <10% 的环节先别碰。
  6. 做 A/B：同轮交替、至少两轮；把负结果和复活条件一起写进文档。
  7. 过门禁：数值正确性 → 生成分布 → 语义/感知 → 必要时人耳/人眼。
  8. 固化：把赢下来的配置写进部署脚本与监控，防止下次重启静默回退。

13.2 Serena 的诞生：五步，零梯度

13.3 为什么一堆整数 codes 能带音色

神经音频 codec（如 RVQ / 多码本量化）把波形压成 [帧, 码本层] 的整数序列。 M5 与 Qwen3-TTS-12Hz 都是 12.5 Hz、16 层码本 的设定；Qwen3-TTS 技术报告明确： 第一层码本偏向语义内容，后续层逐层补充声学细节（音色、气息、环境、韵律）， 因此容量足够用轻量级因果 ConvNet 直接重建波形，不需要单独抽取说话人向量，也不需要扩散模型。

离散化带来的好处

说话人身份被编码成 token 序列后，语言模型可以像处理文本一样"读"它；于是音色变成了上下文，而不是某个需要注入的向量。

为什么必须带逐字转写

M5 的 prompt 里参考文本与 codes 是配套的：模型需要知道这段声音"说的是哪句话"，才能把音色与内容解耦，续写新文本时沿用前者、替换后者。

为什么 3-30 秒就够

零样本克隆不更新权重，只需要足够覆盖音素与韵律的上下文。本项目的 serena 参考约 65 帧（≈5.2 s），服务端上限 375 帧（30 s）。

情感也在这里

语气、语速、停顿同样留在 codes 里。所以"换一段带情绪的参考音频"比写 caption 更可靠（见 13.7）。

13.4 零样本克隆的两条机制

机制做法优点局限本案例
Speaker embedding说话人编码器把参考音频压成固定维向量，注入 LM 的每一步实时、与文本无关、便于跨语言容易丢韵律细节；需要联合训练编码器Qwen3-TTS 的实时克隆路径；llama.cpp 里映射为 mtmd audio encoder
Text–speech pair / in-context把「参考文本 + 参考音频 codes」直接拼进 prompt，让模型续写更好地保留韵律；无需额外编码器占上下文长度；依赖 tokenizer 与训练格式M5 走这条：voices.json 里的 codes 作为前缀行
一句话回答"怎么学的" 没有梯度下降、没有 LoRA、没有微调。Qwen3-TTS 生成的一段音频被重新编码成 M5 自己词表里的离散 token， 作为 few-shot 示范放在 prompt 前面；M5 在自回归续写时把这段示范的统计特征（音色、语速、韵律）延续下去。 这在机器学习里叫 in-context learning（上下文学习），是推理时行为，不是训练时行为。

13.7 情感控制为什么难：一个弱训练槽的案例

M5 的 conditioning 里有 <|caption_begin|>…<|caption_end|> 风格槽，但官方推理把它硬编码为空。 项目做过 7 档 caption（NONE / happy / sad / angry / gentle / 开心 / 悲伤）× 同句同种子，再用 4 个种子做噪声基线：

路径实测证据难度
caption 风格槽非空 caption 让时长 +0~42%，但 F0 / 能量变化落在种子噪声 ±8% 内 → 弱训练槽，无可靠语义情感控制接线低，效果不可靠
情感参考音频克隆codes 强烈迁移音色与韵律；录一段带目标情绪的参考即可低，但情感与音色绑定
DSP 后处理变调 / 变速 / EQ 可预测但机械低
训练侧（情感标注 CPT / SFT）模型卡注明改动 delimiter 需要继续预训练；稀疏训练导致 caption 无效高
实验纪律 种子带来的 F0 采样噪声本身就有 ±8%，所以任何 <10% 的"情感差异"都不可信—— 验证情感/风格效果必须多种子平均。这与 4.1 讲的热漂移是同一类问题：先量噪声底，再谈信号。 相比之下 Qwen3-TTS 的 VoiceDesign 变体是专门用自然语言描述 + instruction 训练过的，属于"训练侧把槽位填满"。

14.2 思考题（先自己算，再展开）

Q11　为什么 7 字句 RTF 0.918 而 24 字句 0.742？这算优化成功吗？
不算。同一份代码，只是固定成本被摊薄。用 T(N)=截距+斜率×N 拟合：截距 ≈152 ms（prefill / 图初始化 / codec prime），斜率 ≈54.7 ms/帧（backbone 6.1 + depth 48.6，codec 被重叠）。 短句 23 帧摊 152 ms 固定开销，每帧多背 6.6 ms；长句 75 帧只多 2 ms。所以看性能必须固定输入长度，或同时报告截距与斜率。
Q12　depth 权重从 21 MB 降到 10.7 MB 只快 9%，你能推出什么？若改成 heads 权重减半呢？
若瓶颈是权重带宽，字节数减半应接近 2×；只有 9% 说明 depth 是提交开销 / 计算主导，继续降位量化没有意义。 而 heads 每帧流式读 34 MB、耗时 13.4 ms ≈ 2.5 GB/s，符合带宽特征；f16→int8 减半后 heads_s 0.94→0.38 s（2.5×），验证了判别。同一个动作效果相反，因为瓶颈类型不同。
Q13　流式首块从 2 帧改成 1 帧，为什么首包反而从 0.285 s 涨到 0.51 s？
少了一个 depth step 省下的时间，小于 codec 多一次 ORT Run 的固定开销 + 该会话的调度/状态准备成本。 这是 5.1 的 F 在 codec 层的翻版：分块越碎，固定成本占比越高。结论是维持 2 帧，并把"1 帧更慢"写进代码注释防止后人重试。
Q14　int8 让 codes 翻转 90%，为什么还能上线？什么情况下你必须否决一个量化？
首帧 0/16 翻转证明没有系统性数值误差；之后是 next_hidden 反馈放大 1-ulp 差异造成的混沌分叉，等价换随机种子。 门禁看 ASR（语义）、音频统计族（分布）、模式内确定性 0% 翻转、人耳。 否决条件是感知层面的系统性偏移：backbone Q14 让音频短 16%、语速变快，ASR 全对也不行；或 codec 激活×激活量化掉 1.3 dB。
Q15　"用 Qwen3-TTS 的音色"这句话里，梯度更新发生在哪里？
迁移过程里一次都没有。Qwen3-TTS 自己的音色能力来自它预训练 / 后训练（含 speaker fine-tuning）时学到的映射； M5 只是把 Qwen 生成的一段音频重新编码成自己词表里的 codec codes，作为 prompt 前缀做 in-context learning。 运行时既不加载 Qwen 也不更新权重。真正"把槽位训练出来"的例子是 Qwen3-TTS 的 VoiceDesign（自然语言描述控制）， M5 的 caption 槽因训练稀疏而弱——这正是"槽位存在 ≠ 槽位可用"。
Q16　如果让你继续把 RTF 从 0.75 往下压，下一步做什么？
先别急着动任何模块——这道题在 2026-11-15 被三项实测改写了（第 10、11 章）。 ① 天花板不是 2.1×：算上 heads 后 depth 上限只有 1.78×，而且 codec 与 depth 并行， wall ≈ backbone + max(depth, codec) + prefill；只做草稿会被 codec 卡住。 ② 三条看似可行的路全部排除：单边旋钮与资源让渡（日志 §13，48 次 A/B 无一快于默认）、 codec 单独优化（被 max 吃掉）、学习型草稿（日志 §14，α_oracle ≈ 0.18 ≪ 0.72 盈亏平衡）。 ③ 后续 KV32 和产品分块优化把同一条 69 帧样句的服务端 WAV RTF 降至 0.677（日志 §16、§25）。 下一轮先对当前默认配置重测稳态关键路径；联合重训 depth 和 codec 的收益仍需实验验证（日志 §30）。 这题真正考的是：先看清依赖结构与并行结构，再判断某个优化能不能兑现。
